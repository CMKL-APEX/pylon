Pylon

Introduction

Pylon gives virtual machines physical CPU cores for as long as they have work, and takes the cores back as soon as they don’t. It’s part of CMKL-APEX/pylon, a fork of Cloud Hypervisor built for the Glidex cloud suite.

The usual ways to resize a VM’s CPU are slow. ACPI CPU hotplug takes milliseconds per vCPU and goes through the guest’s CPU online/offline path. Leaving vCPUs to the host’s fair scheduler means time-slicing them against each other on a millisecond scale. Pylon aims to move a physical core from one VM to another in microseconds. It does this with a shared-memory page that both the guest and the host read and write, a polling arbiter on a dedicated host core, and a Linux sched_ext scheduler that switches a core to its new owner without going through the normal scheduler.

Status. Pylon is under active development. Core arbitration, parking and waking, metering and the sched_ext dispatcher work. Cooperative revocation, which is how a running VM is asked to give a core back, doesn’t work end to end yet. Parking vCPUs inside KVM is a prototype behind an environment variable. See Status and roadmap before relying on any behavior.

Features

  • Elastic vCPUs. A Pylon VM boots with all of its vCPU threads, but only initial_active_vcpus of them run. The others are parked and cost nothing until pylond gives them a core.
  • A per-host core arbiter. pylond owns a set of host CPUs and hands them to VMs by demand and priority. It polls guest demand about every microsecond on a dedicated core, with no heap allocations, locks or blocking calls in its loop.
  • Per-VM policy. Each VM has a minimum and maximum number of cores and a priority weight. They can be changed at runtime without restarting the VM.
  • Scale to zero. A VM can hold no cores at all and be woken when its next timer is due.
  • Kernel-level handoff. On a kernel with sched_ext, the scx_pylon BPF scheduler runs whichever vCPU thread pylond assigned to a core, read straight from a memory-mapped BPF map.
  • Metering. pylond counts each VM’s core-microseconds, cooperative yields and forced preemptions, over its control socket and as Prometheus metrics.

Quick start

This page builds Pylon from source, starts the pylond arbiter and boots a VM with eight vCPUs, two of them running.

You need an x86_64 or aarch64 Linux host with KVM, and a user that can read and write /dev/kvm. On aarch64, read the aarch64 requirements first.

1. Build

Install Cloud Hypervisor’s usual build dependencies, plus clang, libelf and zlib for the scx_pylon BPF object:

sudo apt-get install -y build-essential clang llvm libelf-dev zlib1g-dev pkg-config
git clone https://github.com/CMKL-APEX/pylon.git && cd pylon
cargo build --release -p cloud-hypervisor -p pylond

This produces target/release/cloud-hypervisor and target/release/pylond. You can instead download both from a release.

2. Start pylond

pylond arbitrates the host CPUs you give it with --cores, and uses host cores 0 and 1 for itself. Keep those three sets apart: don’t list 0 or 1 in --cores. Core 1 is where the polling engine runs; move it with --engine-cpu (on a host with big and little cores, pick a big one) and keep it out of --cores too.

sudo ./target/release/pylond --socket /run/pylon/pylond.sock --cores 2-7 \
    --socket-group "$(id -gn)" --socket-mode 660

--socket-group and --socket-mode let your own group, and so your non-root VMM, use the socket. Without them, the socket keeps root’s umask (0755), and only root can connect.

On a kernel with sched_ext, pylond also attaches the scx_pylon scheduler. That scheduler then schedules every task on the host, not only VMs, until pylond exits. Add --no-scx to keep the host’s normal scheduler (see Kernel scheduling with scx_pylon).

3. Boot a Pylon VM

Add --pylon to an ordinary Cloud Hypervisor command line:

./target/release/cloud-hypervisor \
    --kernel vmlinux \
    --disk path=focal.raw \
    --cmdline "console=ttyS0 root=/dev/vda1 rw" \
    --cpus boot=8 \
    --memory size=2G \
    --serial tty --console off \
    --pylon socket=/run/pylon/pylond.sock,vm_id=1,initial_active_vcpus=2,min_cores=1,max_cores=8

The VM boots with eight vCPUs, and the guest brings all eight online. vCPUs 0 and 1 keep running. Once the guest reports that it is up (the guest agent’s first heartbeat), pylond asks the VMM to park vCPUs 2–7, and wakes them again when there’s demand. Without a guest agent the other vCPUs are never parked: the VM then behaves like an ordinary one.

Give every VM its own vm_id. It defaults to 1, and pylond rejects a VM whose id is already registered by a running VMM.

4. Look at it

Ask pylond for its view of the VM over its socket:

echo '{"action":"stats"}' | sudo socat - UNIX-CONNECT:/run/pylon/pylond.sock

The reply lists every registered VM with its current cores, policy and counters. To export them as Prometheus metrics, start pylond with --metrics-port 9100 and fetch http://127.0.0.1:9100/metrics. See Policy and monitoring.

Concepts

The words

Managed CPUs are the host CPUs listed in pylond --cores. Only these are given to VMs. pylond itself runs on host cores 0 and 1.

Shared page. An 8 KiB memory region per VM, backed by a memfd the VMM creates. It’s mapped into the VMM, into pylond, and into the guest at a fixed guest-physical address (0xFEDF_0000 by default). It holds a header, guest telemetry, and one 64-byte slot per vCPU. The same file holds a host page after it, which the guest doesn’t see: the VMM and pylond keep the park state and thread IDs they act on there.

Telemetry is what the guest writes about its own demand: how many threads are runnable, how long the oldest one has waited, and when its next timer fires.

vCPU states. Each vCPU slot has a state:

StateMeaning
RUNNINGThe vCPU thread runs guest code.
PARKEDThe vCPU thread is blocked in the VMM, waiting to be woken. It uses no CPU. A VM that parks inside KVM (below) keeps a parked vCPU halted in KVM instead.
WAKINGDefined but no longer written: a vCPU that has just been given a core stays PARKED until its thread wakes and the VMM writes RUNNING.
PARKINGThe guest asks to park this vCPU. The VMM parks it at its next exit to userspace. The pv-pylon module writes it when pylond revokes the vCPU (see Inside the guest).

Park and wake. Parking a vCPU blocks its host thread on an eventfd instead of running KVM_RUN. Waking it writes that eventfd. To the guest, a parked vCPU looks like a vCPU that isn’t being scheduled.

Parking inside KVM. The default on KVM hosts, x86_64 and aarch64, chosen with --pylon park=kvm|vmm. A parked vCPU stays inside KVM_RUN, halted, so an interrupt such as a timer or an IPI wakes it. A woken vCPU runs on its VM’s CPUs without a core of its own, and stays PARKED. pylond gives it a spare core at once (an idle one, or one a VM that wants no core holds), and any core if it stays woken for 4 ms. It is meant to run with scx_pylon. See Status and roadmap.

Assign. pylond assigns a managed CPU to one vCPU of one VM. It records the assignment in the vCPU’s slot (assigned_pcpu) and in the pCPU owner table, which maps each host CPU to the thread ID of the vCPU that owns it. scx_pylon reads that table.

Revoke. To move a core from a donor VM to a recipient VM, pylond sets the donor vCPU’s revoke_requested flag and gives it a grace period of 8 µs to park. A donor that parks in time has made a cooperative yield. When the deadline passes, the revocation counts as a forced preemption: pylond signals the donor’s thread so the VMM parks it, and hands the core over once it has. If the donor still hasn’t parked 50 µs after the first signal, pylond hands the core over anyway, which is counted as a handoff without park. It keeps signalling that donor until it parks, waiting longer between signals each time, up to 1 ms. See Status and roadmap for how much of this path works today.

Critical section. A vCPU’s in_critical_section is meant to be set while the guest holds a spinlock, handles an interrupt or has preemption disabled on it. pylond prefers donors that aren’t in one, because preempting a lock holder stalls every other vCPU waiting for that lock. No guest component sets it yet.

Policy. Each VM has min_cores, max_cores and a priority_weight. They are set with --pylon at boot and can be changed at runtime over pylond’s control socket.

Urgency. pylond’s score for how badly a VM needs another core. It grows with how long the guest’s oldest runnable thread has waited, multiplied by the VM’s priority weight. A VM below its min_cores gets a large boost, and a VM waking from zero cores gets the maximum.

Scale to zero. A VM with no cores at all. pylond wakes it when a guest timer comes due: one that was armed on a vCPU when the VMM parked it, or the guest’s next_timer_tsc. A VM that parks inside KVM is woken instead when one of its vCPUs stays woken for 4 ms.

Core-microseconds. The metering unit: one managed CPU assigned to a VM for one microsecond.

What doesn’t work yet

Parking inside KVM has limits. It is the default on x86_64 KVM hosts (--pylon park=kvm), because it stops the stalls in unmodified guests and costs no throughput, nested and on bare metal (spec 08 §7.4, §7.5). But:

  • It needs scx_pylon. pylond without it rejects such a VM; use park=vmm there.
  • Wake latency has a tail of about 0.45 ms when another VM is busy and two vCPUs of a VM share a core: a woken vCPU spins until KVM’s pause-loop exit yields to the other. It was about 1.9 ms before scx_pylon honoured those yields (#52).

Cooperative revocation, within the grace period. The parts exist (pylon-kick and pv-pylon), but:

  • Too slow for the grace period. Under the real pylond, a guest takes 80–140 µs on average to park after a revocation, far more than pylond’s 8 µs grace period, so revocations end in a forced park. A longer grace makes them cooperative but gains no throughput, so the guest’s yield has to get faster (#74). On the bare-metal x86_64 host, the kick takes 4–32 µs to reach the guest, and the guest then takes 16–64 µs to ask to park: kernel code runs that slowly on that host, in a guest or not (spec 09 §9). So forced parks stay the default in v0.0.8. This was measured on Zen 2 only, which needs some of the costliest x86 mitigations; newer x86 CPUs may do better and are still to be measured.
  • Handoffs take about 100–125 µs. On bare metal, from a revocation request to the recipient vCPU running takes 100–126 µs at the median (#53; see Performance and benchmarks), against a 3–6 µs target. Most of it is the VMM’s 40–60 µs to park or wake a vCPU after a signal, which isn’t explained yet (#54).
  • No module, no cooperation. A guest without pv-pylon never cooperates: every revocation ends in a forced park.

Other gaps (tracked as K1–K7 in the status tracker’s known issues):

  • Scale to zero. Without parking inside KVM, a VM that holds no cores is woken when a timer it armed before its vCPUs parked comes due: the VMM reads each vCPU’s timer as it parks it (on x86_64 the TSC-deadline timer, on aarch64 the EL1 virtual timer). Inside KVM, KVM fires the timer itself. Arriving packets don’t wake a VM with no core: nothing on the host feeds the receive doorbell yet (#57).
  • Critical sections. Nothing writes in_critical_section, so donor selection can’t avoid lock holders. It needs guest kernel hooks, not just the module (#56).
  • Counter scaling. pylond converts the guest’s counter values with the offset the VMM measures, assuming the guest counter runs at the host’s rate. A VM restored with a different TSC rate would break that, but restore doesn’t support Pylon yet anyway.
  • The shared page’s address. The page is no longer reported to the guest as RAM, and the layout declares it, but it still sits at the fixed address 0xFEDF_0000 instead of a PCI BAR (#59).
  • Lifecycle. Snapshot and live migration are refused with --pylon (#61), and so is resizing the vCPUs (#60). A pylond restart is handled: VMs run unmanaged while it is away, and register again when it is back.
  • PCI ID. pylon-kick uses a provisional ID, 0x1AF4:0x10F0, from QEMU’s experimental range (#64).

Release notes

v0.0.8

The first Pylon release. Pylon is a fork of Cloud Hypervisor; the VMM keeps upstream’s version number (55.0.0), and the Pylon components (pylond, scx_pylon, pylon-abi, pylon-guest-agent and the pv-pylon guest module) are numbered 0.0.8. The files of a release are listed in Building and installing.

What’s in it

  • --pylon: a VM gets a shared page with pylond, boots with only initial_active_vcpus running, and parks the rest once the guest agent reports that it is up.
  • pylond: arbitrates a set of host CPUs between Pylon VMs. It wakes parked vCPUs of VMs with demand, reclaims idle cores, and takes cores from other VMs by urgency and priority_weight, within each VM’s min_cores and max_cores. A donor that doesn’t park within 8 µs is parked by force. Policy can be changed at run time over the control socket, and usage is exported as Prometheus metrics.
  • scx_pylon: a sched_ext scheduler, built into pylond, that runs each managed CPU’s assigned vCPU thread and keeps vCPU threads apart from their SMT siblings.
  • Guest side: pylon-guest-agent reports the guest’s demand, and the optional pv-pylon module with the pylon-kick device lets a guest park a vCPU at a safe point when asked.
  • aarch64: pylond, scx_pylon and the VMM side build and run on aarch64 hosts.

See Status and roadmap for what works and what doesn’t.

Highlights of this release

  • vCPUs park inside KVM by default on KVM hosts, x86_64 and aarch64 (--pylon park=kvm, #51). A parked vCPU stays halted in KVM, so a timer or an IPI wakes it. This removes the soft lockups and RCU stalls of guests without pv-pylon that hold fewer cores than they have vCPUs, at no throughput cost, nested and on bare metal (spec 08 §7.4–§7.5). park=vmm keeps the previous park, in the VMM.
  • aarch64 runs real guests end to end, with scx_pylon attached and vCPUs parked inside KVM, after a fix to how a suspended aarch64 vCPU wakes (#62).
  • VMs survive a pylond restart (#60). A VMM keeps its registration open; when pylond goes away, it wakes every parked vCPU and runs the VM unmanaged, and it registers again once a new pylond listens. A VM started before pylond registers once it appears (Running pylond).
  • pylond refuses a VM that parks inside KVM when scx_pylon isn’t attached, and the VMM now reads pylond’s reply: it logs whether the registration was accepted, and where its vCPUs park.
  • Core scheduling: on kernels without the sched_ext core-scheduling fixes, where pylond makes the kernel refuse core scheduling (#15), a --pylon VM now runs without it and logs one warning, instead of failing to start. scx_pylon keeps its vCPU threads apart from their SMT siblings.
  • min_cores is a floor under demand: a VM with runnable work is raised to min_cores first, and an idle VM holds no cores (#58).
  • The VMM keeps the shared page in a sealed memfd instead of a file under /dev/shm, and pylond keeps the state it acts on in a host page the guest doesn’t map. --pylon shm=<path> is gone.
  • The control socket is per user: a VM’s policy and stats are available only to the user that registered it, root, and pylond’s own user. Each connection has 5 seconds, and at most 64 are served at once. Give the socket to a group of the users your VMMs run as (Running pylond).
  • pylond checks what a VM registers with: the shared memory file must be a memfd whose size is sealed, and the kick and wake descriptors eventfds. A VM whose eventfd write blocks is dropped.
  • pv-pylon checked against the real pylond (#55): cooperative parks work end to end, but take longer than the grace period (see below).

Requirements

  • A Linux host with KVM, x86_64 or aarch64.
  • For the default park=kvm: a kernel with CONFIG_SCHED_CLASS_EXT (6.12 or later), so that pylond can attach scx_pylon. On other kernels, start VMs with --pylon ...,park=vmm.
  • The released pylond and scx_pylon need glibc 2.39 or later, libelf, zlib and zstd.

Compatibility

  • Shared-page ABI version 3. Parking inside KVM changed what two shared-page fields mean, so the ABI version is now 3. pylond, the VMM, pylon-guest-agent and pv-pylon from this release work together; builds from before #51 (version 2) refuse the page. Update all of them together.
  • Update the VMM and pylond together. Besides the shared page, the VMM’s shared memory now holds a host page with its own version (3), which pylond requires. The guest side is unaffected.
  • --pylon shm=<path> is gone, and the VMM refuses a command line that has it: remove it. Every --pylon key is now optional.
  • PYLON_PARK_IN_KVM is gone; use --pylon park=kvm|vmm.
  • Snapshot, restore and live migration are refused for --pylon VMs.
  • pylon-kick’s PCI ID (0x1AF4:0x10F0) is provisional and may change (#64).

Known limits

  • Wake latency has a tail of about 0.45 ms when another VM is busy (about 1.9 ms in v0.0.8-rc1), nested and on bare metal (#52).
  • Cooperative parks are too slow for the grace period: a guest takes 80–140 µs to park after a revocation, against pylond’s 8 µs grace, so revocations end in a forced park (#74).
  • vCPU hotplug is refused for VMs with --pylon (#60).
  • A VM with no core isn’t woken by arriving packets (#57).

The next release, v0.0.9, is tracked on its milestone.

Running a Pylon VM

A Pylon VM is an ordinary Cloud Hypervisor VM started with one more option, --pylon. This page explains what to put in it and what happens when the VM starts and stops. Every key is listed in The –pylon option.

The option

--pylon [socket=<path>,gpa=<addr>,initial_active_vcpus=<n>,min_cores=<n>,max_cores=<n>,priority_weight=<n>,vm_id=<id>]

Every key is optional. A typical VM on a host running pylond:

--cpus boot=8 \
--pylon socket=/run/pylon/pylond.sock,vm_id=17,initial_active_vcpus=2,min_cores=1,max_cores=8,priority_weight=200

Choosing the numbers

vCPUs. Pylon manages max(boot, max) vCPUs from --cpus, and at most 64. Every one of them gets a host thread at boot, and the guest sees all of them online. Pylon then decides which of them actually run. Give the VM as many vCPUs as it could ever use; the parked ones cost a thread each and no CPU time.

initial_active_vcpus is how many vCPUs run from the start: vCPUs 0 to n-1. The rest run during boot, so the guest can bring them online, and are parked once the guest reports that it is up (its first heartbeat); until then, or if no guest agent ever reports, they run. It defaults to the boot count, so without it every vCPU starts running. Keep at least 1, because the guest boots on vCPU 0.

min_cores and max_cores bound how many host CPUs pylond gives the VM. max_cores defaults to the number of vCPUs. min_cores defaults to 1. When the VM has runnable work, pylond raises it to min_cores first, before giving cores to VMs above their minimum. min_cores is a floor under demand, not a reservation: a VM that reports no runnable threads gets no cores, whatever its min_cores, so an idle VM leaves its cores to others. Its first runnable thread brings it back to min_cores.

priority_weight (default 100) multiplies the VM’s urgency. Between two VMs whose oldest runnable thread has waited equally long, the one with twice the weight wins. It’s relative: only the ratio between VMs matters.

vm_id names the VM to pylond. Set it, and keep it unique on the host. It defaults to 1. While a VM’s VMM runs, pylond rejects any other VM that registers with the same id, and logs it. The rejected VM boots, but pylond never manages it.

The VMM keeps the VM’s shared page in a sealed memfd with no path. Earlier versions took a file path as shm=<path>; remove it from old command lines, which the VMM now refuses.

gpa is where the guest finds the page (default 0xFEDF_0000). It must be 4 KiB-aligned. Change it only together with the guest side, which looks there by default.

What happens at boot

  1. While parsing its options, the VMM creates and zeroes the shared page, writes the header (magic, ABI version, vCPU count, vm_id), and creates two eventfds per vCPU.
  2. While setting up guest memory, the VMM maps the page into guest memory at gpa.
  3. If socket is given and exists, the VMM then registers the VM with pylond, passing the shared page and the eventfds, and logs whether pylond accepted it. If the socket doesn’t exist yet, the VM boots without registering; if connecting fails or pylond rejects the VM, the VMM logs a warning and boots anyway, unmanaged. It doesn’t retry, so start pylond before the VMs.
  4. Each vCPU thread records its host thread ID in its slot and enters the guest as RUNNING. vCPUs from initial_active_vcpus on are also tagged park_on_boot.
  5. When the guest agent’s first heartbeat arrives, pylond asks the VMM to park the tagged vCPUs. They park at once, and these parks don’t count as yields.

From then on, pylond wakes parked vCPUs when the guest reports demand and a managed CPU is free.

Parking inside KVM

On a KVM host, x86_64 or aarch64, vCPUs park inside KVM by default (--pylon park=kvm). A parked vCPU stays halted in KVM, so a timer or an IPI wakes it. The VMM logs where its vCPUs park, at info level, when it registers with pylond. This needs pylond with scx_pylon: without it, pylond rejects the VM’s registration. Use park=vmm to park in the VMM instead, for example with a guest that runs pv-pylon on a host without scx_pylon. See The –pylon option and The scx_pylon dispatcher.

What happens at shutdown

When the VM shuts down, the VMM wakes every parked vCPU thread so that it can exit. The shared-page file is not removed. Delete it yourself, or reuse the path for the same VM next time: the VMM zeroes it at start.

pylond holds a pidfd for each VM’s VMM. Within about a second of the VMM exiting, it removes the VM’s registration and frees the managed CPUs the VM held. The VM’s vm_id is then free for its next start.

Things to avoid

  • Snapshot, restore and live migration. Pylon state isn’t saved or moved, so the VMM refuses to snapshot or migrate a VM with --pylon: its pylon-kick device fails the snapshot.
  • vCPU hotplug (ch-remote resize with --cpus). The VMM refuses it for a VM with --pylon: pylond learns a VM’s vCPUs once, at registration. Boot the VM with all its vCPUs (--cpus boot=N) and let pylond park those it doesn’t need; initial_active_vcpus sets how many run at boot.

Inside the guest

Pylon needs no changes to the guest to boot it. Without a guest component, though, pylond has no demand signal, and no heartbeat tells it that the guest has booted. Every vCPU keeps running, and the VM behaves like an ordinary one. This page explains what the guest sees and how it reports demand.

What the guest sees

  • All vCPUs are online. A parked vCPU is still online in the guest. It just isn’t scheduled on the host, the way a vCPU of an overcommitted host sometimes isn’t. The guest’s scheduler may put work on it; that work waits until pylond wakes the vCPU. A VM that parks inside KVM is different: an interrupt sent to a parked vCPU wakes it, and it runs for a while without a core of its own.
  • The shared page, 8 KiB at guest-physical address 0xFEDF_0000 (or the gpa you set). It starts with the header: magic 0x5059_4C4F_4E56_4D31 ("PYLONVM1"), ABI version 3, the number of vCPU slots and the VM’s id. See Shared-memory ABI for the layout.

Reporting demand: pylon-guest-agent

pylon-guest-agent is a small userspace daemon for Linux guests. It maps the shared page through /dev/pylon when the pv-pylon module is loaded, or through /dev/mem otherwise. Every interval (50 ms by default), it:

  • writes the number of runnable threads, from the fourth field of /proc/loadavg (or procs_running in /proc/stat), to runnable_threads. Both count the agent itself, which is running while it reads them, so the agent subtracts 1: an idle guest reports 0, and pylond can move all its cores to other VMs;
  • increments guest_heartbeat, which also tells pylond that the guest has booted, so it parks the vCPUs beyond initial_active_vcpus;
  • when there are more runnable threads than running vCPUs, records the guest counter (the TSC, or CNTVCT_EL0 on aarch64) at which that started in head_wait_tsc, keeps it while threads still wait, and clears it once there are enough running vCPUs.

Build it on the host and copy it into the guest:

cargo build --release -p pylon-guest-agent
# in the guest, as root:
./pylon-guest-agent                       # run, sampling every 50 ms
./pylon-guest-agent --interval-us 10000   # sample every 10 ms
./pylon-guest-agent --status              # print the page and exit

It needs root. Without pv-pylon, it also needs a guest kernel that allows /dev/mem mappings of the page’s address. It pins itself to guest CPU 0; pick another with --cpu, but only one of the initial_active_vcpus, since an agent on a parked vCPU can’t report demand. All its options are in Other tools.

The agent only writes telemetry. It leaves vCPU states and revocation requests alone: a userspace process can’t stop a vCPU, so it can’t agree to park one. Older versions of the agent marked revoked vCPUs as parked while they kept running; this version doesn’t, and a mismatched agent refuses to start against a version-2 page.

Parking cooperatively: the pv-pylon module

A userspace process can’t stop a vCPU, so the agent can’t agree to give a core back. pv-pylon is a Linux kernel module that can (pylon/guest/linux/). It binds to the pylon-kick PCI device (1af4:10f0, a provisional ID) that the VMM adds to every --pylon VM.

When pylond revokes a vCPU, the module parks it at the next safe point: no spinlock held, preemption enabled. The vCPU then gives up its core cooperatively, instead of being stopped by a signal once the grace period runs out.

Build it against the guest kernel’s headers, and load it as root:

make -C pylon/guest/linux KDIR=/lib/modules/<guest-kernel>/build
# in the guest:
insmod pv_pylon.ko
cat /sys/bus/pci/drivers/pv_pylon/*/stats

Start pylon-guest-agent after loading the module. It then maps the page through /dev/pylon; on x86 a /dev/mem mapping fails once the module has the page mapped.

stats counts:

  • the kicks received;
  • kicks that arrived with nothing to do (spurious);
  • kicks passed on to another CPU (forwarded);
  • the parks;
  • wakeups that found the revocation already handled (stale).

The module needs Linux 6.3 or later. It has been run on Ubuntu 6.8 and 7.0 guests on x86_64; aarch64 is untested.

Limits

  • Demand is reported late. The agent samples at a fixed interval, so demand reaches pylond milliseconds late, and Pylon’s microsecond handoff needs it sooner.
  • No critical-section or preemption reporting. pv-pylon doesn’t yet report kernel critical sections, and doesn’t make other vCPUs treat a parked vCPU as preempted. Both need guest kernel changes, not just a module.
  • The cooperative park is slow. On the hosts tested so far it is slower than pylond’s 8 µs grace period. Until the latency work (S6), many revocations still end in a forced park.

Pylon runs on aarch64 KVM hosts with aarch64 Linux guests. What it needs beyond the table above:

  • KVM only. --pylon is rejected at start-up on MSHV on aarch64, which can read neither the guest’s counter nor its timer.
  • FEAT_S2FWB, which every Armv8.4 or later core implements.   • The shared page is at guest address 0xFEDF_0000, 64 KiB aligned, in the 32-bit reserved hole, outside the FDT’s memory node.

Running pylond

pylond is the per-host core arbiter. Run exactly one per host. Every option is in the pylond reference.

Host CPUs

pylond uses three groups of host CPUs:

CPUsUsed forSet by
0Control plane: the Unix socket, VM registrations, policy and stats requests, the metrics server. Mostly idle.Fixed
1 (default)Arbitration engine: polls every VM’s shared page about every microsecond. It keeps this CPU fully busy.--engine-cpu, default 1
--coresManaged CPUs, given to VMs’ vCPUs.--cores, default 2-7

--cores takes a comma-separated list of CPUs and ranges, such as 2-7 or 4-15,20-31.

  • Don’t put 0 or the engine CPU in --cores. pylond warns about the engine CPU but doesn’t check CPU 0. Its own threads would then compete with VMs on those CPUs.
  • The engine thread spins at all times. On x86_64 CPUs with WAITPKG and aarch64 CPUs with FEAT_WFxT, it waits with TPAUSE or WFET between sweeps, which uses less power than spinning; on others, it uses PAUSE or a spin hint. The engine logs timed_wait=true or false at start, with the CPU it pinned to.
  • Once a guest reports it is up (a non-zero guest_heartbeat, which only pylon-guest-agent writes), Plane 1 asks the VMM to park the vCPUs beyond initial_active_vcpus, signalling each thread; it checks once a second and logs VM <id>: asked <n> booted vCPU(s) to park. Without the agent, those vCPUs keep running.
  • The engine is pinned to CPU 1 unless you pass --engine-cpu. On a host with big and little cores, pick a big one; pylond warns if it is also in --cores.
  • Keep other work off the engine CPU, for example with the kernel’s isolcpus= or nohz_full= boot options, or a cgroup cpuset that excludes it. Any interruption of the engine delays every handoff on the host. With scx_pylon, the engine owns its CPU, so vCPU threads don’t run there, but kernel threads bound to that CPU still do.
  • If pinning fails, pylond logs a warning and keeps running unpinned.

pylond doesn’t stop other processes from running on the managed CPUs. Keep VMMs’ non-vCPU threads and host services on other CPUs, with cpusets or taskset, or use scx_pylon.

The control socket

pylond listens on --socket (default /run/pylon/pylond.sock). VMMs register on it, and you use it to change policy and read stats (Policy and monitoring).

At start, pylond removes any file already at that path and creates the socket. --socket-group (a group name or GID) and --socket-mode (octal, such as 660) set its group and permissions; without them it keeps pylond’s umask and group, which as root means only root can connect. The socket appears at the path only once pylond accepts connections and has its group and mode: pylond creates it as <path>.tmp and renames it.

pylond records the UID of the process that registers each VM. A VM’s policy can be changed, and its stats read, only by that UID, by root, and by pylond’s own UID; other users see neither. But anyone who can write to the socket can register VMs: register under a vm_id before the VM that should have it starts (that VM is then rejected and runs unmanaged), or register VMs that ask for cores. Give access only to the users your VMMs run as, through a group of their own rather than a shared one such as kvm (see the systemd unit).

Each client gets 5 seconds to send its request and read the response, and the socket serves at most 64 clients at a time; further ones are closed at once. The metrics server has the same limits. When it runs out of file descriptors, pylond logs the failed accept and tries again 100 ms later. At start it raises its soft limit on open files to the hard limit: each registered VM holds up to 129 of them.

Start order and restarts

pylond and its VMs can start in either order, and pylond can be restarted while VMs run (spec 10):

  • A VM keeps its registration open. When pylond exits, for any reason, the VMM finds out at once. It wakes every parked vCPU and runs the VM unmanaged: all its vCPUs run where the host’s scheduler puts them, and none park. The VMM logs pylond closed the session of VM <id>; it runs unmanaged until a pylond listens at <path> again.
  • A VM registers again when a new pylond creates the socket. The VMM watches the socket’s directory, and checks the path every 5 seconds as well. pylond then parks the vCPUs beyond initial_active_vcpus, as after the VM’s boot, and gives the VM cores from there.
  • A VM that starts before pylond runs unmanaged and registers once the socket appears.

What a restart loses: policy changed over the control socket (a VM registers again with its --pylon values), and the stats and metrics counters. A VMM that pylond refuses waits for the next new socket before it tries again. VMMs from v0.0.8-rc1 and earlier register once and don’t come back after a restart.

Stopping

pylond has no signal handlers of its own: SIGTERM and SIGINT end it immediately. The kernel then detaches scx_pylon, if it was attached, and the host’s normal scheduler takes over. Each VMM sees its session end and runs its VM unmanaged, with every vCPU awake, until a pylond starts again (Start order and restarts). The socket file is left behind and removed at the next start.

VMs that park inside KVM

A VMM started with --pylon park=kvm, the default on x86_64 KVM hosts, parks vCPUs halted inside KVM instead of blocked in the VMM, so an interrupt wakes a parked vCPU. It logs Pylon: VM <id> parks vCPUs inside KVM (spec 08). pylond needs no option for it. What changes on the host:

  • It needs scx_pylon. scx_pylon runs a woken vCPU only on CPUs its VM owns and reports it to pylond, which then gives it a spare core at once, and a core to a VM whose vCPU stays woken for 4 ms. pylond without scx_pylon rejects such a VM’s registration, and logs Rejected registration; start the VM with park=vmm on such a host (Kernel scheduling with scx_pylon).
  • Halt polling is off for that VM. The VMM sets the VM’s halt polling limit to 0, so a parked vCPU costs no host CPU. It logs Pylon: failed to turn halt polling off if it can’t.
  • Parks are bounded. A vCPU that the guest or a revocation parked runs again, still parked and without a core, after 4 ms. Boot parks have no bound.
  • Re-signals back off, for every VM. A donor that doesn’t park is signalled again at intervals that double from 10 µs up to 1 ms. In a VM that parks inside KVM, an x86_64 vCPU with interrupts disabled doesn’t park until the guest enables them again.

Logging

pylond logs to standard error through env_logger. Set RUST_LOG (warn, debug) to choose the level; the default is info. At info, it logs the managed CPUs, whether scx_pylon was attached, registrations, and policy changes. If the kernel rejects scx_pylon, libbpf prints the verifier’s log just before pylond’s warning.

Kernel scheduling with scx_pylon

scx_pylon is a Linux sched_ext scheduler, written in BPF and built into pylond. When it’s attached, the kernel runs each managed CPU’s assigned vCPU thread as soon as that thread is runnable, without going through the host’s fair scheduler.

What it does

pylond and scx_pylon share one table: for each host CPU, the thread ID of the vCPU that owns it. pylond writes the table through a memory-mapped BPF map, with no system calls. The scheduler reads it:

  • When pylond gives a CPU to a vCPU, it also kicks that CPU, so the CPU stops what it runs and picks the vCPU at once, even one that was already waiting to run.

  • When a vCPU thread wakes, scx_pylon looks up the CPU that thread owns and queues it there. If the thread was last on another CPU, it kicks the owned CPU so the switch happens at once.

  • When a CPU needs its next task, scx_pylon dispatches the CPU’s owner, and preempts the task on that CPU if it isn’t the owner.

  • When KVM wakes a parked vCPU of a VM that parks inside KVM, scx_pylon runs it only on a CPU its VM owns, taking turns with the owner in 100 µs slices, and marks it woken for pylond. If the VM owns no CPU, the vCPU runs like any other managed vCPU thread.

  • Every other task is placed by sched_ext’s default CPU selection.

Without scx_pylon, the same table exists in pylond’s memory but nothing reads it. Parked vCPU threads are still woken and blocked through eventfds, and the host’s fair scheduler decides where and when they run. A VM that parks inside KVM needs scx_pylon: without it, its woken vCPUs run on any CPU and pylond doesn’t know they run.

What it means for the host

scx_pylon schedules every normal task on the host, not only VMs, for as long as it’s attached. That includes host services, VMM device threads and your shell. It detaches when pylond exits, including when pylond crashes, and the host returns to its normal scheduler.

Before attaching it on a shared host:

  • An owned CPU runs its vCPU thread until it blocks. Tasks that can run only on that CPU, such as per-CPU kernel threads, get it for up to 20 ms at a time; other tasks wait or run elsewhere. Keep host work off the managed CPUs and their SMT siblings.
  • The kernel watches sched_ext schedulers. If a runnable task is starved for too long (30 s by default), the kernel ejects the scheduler and logs why in dmesg. The host then runs on its normal scheduler while pylond keeps running without scx_pylon.
  • Only one sched_ext scheduler can be attached at a time. If another is attached, attaching scx_pylon fails.

Core scheduling

On kernels that lack upstream fixes to sched_ext, it can’t be used together with kernel core scheduling (PR_SCHED_CORE): the host hangs or crashes (issue #15). Ubuntu’s 7.0.0-42 is one such kernel. Core scheduling turns on for the whole host as soon as any process asks for it, and Cloud Hypervisor does by default (core_scheduling=vm), so one VM started by anyone is enough.

So, on such a kernel, pylond guards scx_pylon:

  • It doesn’t attach while any thread has a core scheduling cookie. The log names the thread.
  • While attached, it refuses requests for new cookies. Pylon’s Cloud Hypervisor then starts a VM with --pylon without core scheduling, and logs a warning once (Pylon: core scheduling refused (EPERM)). It still fails a VM without --pylon, with Error enabling core scheduling. Upstream Cloud Hypervisor hangs instead, without answering its API, until it is killed with SIGKILL. Start VMs without --pylon with --cpus ...,core_scheduling=off. scx_pylon keeps SMT siblings apart for VMs that pylond manages, from about a second after each vCPU thread starts, whether or not the vCPU has a CPU of its own. VMs it doesn’t manage get no SMT isolation from each other.

pylond logs its decision at startup, for example Core scheduling: kernel lacks the sched_ext core-scheduling fixes (pylon#15); scx_pylon guard on, deny Eperm.

Use --no-scx when the host runs other latency-sensitive work you don’t want under a VM-oriented scheduler, or until you have tested scx_pylon with your workload.

Policy and monitoring

pylond answers policy changes and stats requests on its control socket, and can serve Prometheus metrics over HTTP. The message formats are in Control socket protocol and the metrics in Metrics.

The examples use socat. Any client that writes one JSON object to the socket and reads one back works.

Changing a VM’s policy

Send the VM’s id and the fields to change. Fields you leave out keep their value.

echo '{"vm_id":17,"max_cores":4,"priority_weight":300}' \
  | socat - UNIX-CONNECT:/run/pylon/pylond.sock

{"accepted":true,"message":"policy updated","min_cores":1,"max_cores":4,"priority_weight":300}

The new values apply from the engine’s next sweep, within microseconds. Lowering max_cores below what a VM holds doesn’t take cores away immediately. The VM gives them back as its vCPUs park, or when another VM needs them.

pylond rejects an update ("accepted": false) for a VM it doesn’t know, and one that would leave max_cores at 0, min_cores above max_cores, or max_cores above the VM’s vCPU count. A priority_weight of 0 is raised to 1.

Policy changes aren’t saved. A VM that restarts, or registers again after pylond restarts, registers with the values from its --pylon option.

Troubleshooting

A VM doesn’t show up in pylond’s stats

Look for these lines in the VMM’s log:

Also check that two VMs don’t share a vm_id. pylond rejects the second while the first VM’s VMM runs, and logs Rejected registration of VM <id>: ... a running VMM already registered this vm_id. The VMM doesn’t see the rejection, so look in pylond’s log.

Parked vCPUs never wake

pylond wakes a parked vCPU only when its VM reports demand above the cores it already has. Check runnable_threads in the stats:

  • Always 0, even while the guest is busy: nothing in the guest writes demand. Run pylon-guest-agent in the guest. (The agent doesn’t count itself, so an idle guest reports 0.)
  • Above zero, but current_cores doesn’t grow: check that the VM’s max_cores is above its current cores, and that a managed CPU is free or a donor VM is above its min_cores. On a host where every managed CPU is taken, a VM waits for a donor with lower urgency.
  • The guest agent fails with an /dev/mem error: the guest kernel doesn’t allow mapping the page’s address through /dev/mem, or the agent isn’t running as root.

The guest hangs or stalls while some vCPUs are parked

The guest sees parked vCPUs as online. Work queued on them, and interprocessor interrupts sent to them (for example TLB shootdowns), wait until pylond wakes the vCPU. Keep initial_active_vcpus high enough for the guest’s normal load. This is a known open question in the design (spec 06, Q2). Parking inside KVM, a prototype, lets an interrupt wake a parked vCPU instead.

One case to avoid in particular: a process that has to keep running, such as the guest agent, sitting on a parked vCPU. If it is the only runnable thread, pylond sees no demand and never wakes that vCPU. The guest agent pins itself to vCPU 0 (--cpu), which never parks; give any other must-run process a CPU among the initial vCPUs too.

Forced preemptions are high

That’s expected for now. A guest without the pv-pylon module never parks cooperatively, and with it the cooperative park is still slower than the 8 µs grace period (Status). pylond then signals the donor’s vCPU thread and the VMM parks it.

Handoffs without park are above zero

pylond gave a core away because the donor hadn’t parked 50 µs after it was first signalled. pylond keeps signalling that donor until it parks, at intervals that double up to 1 ms. Check:

  • The VMM is a version from before kick_signal. Such a VMM registers without one, so pylond can’t signal it. Upgrade it.
  • pylond can’t signal the VMM. It needs the same user as the VMM, or CAP_KILL.
  • The vCPU thread is stuck outside KVM_RUN, for example in a slow device exit. The donor parks at its next exit; look at the VMM’s log.
  • The VM parks inside KVM and the guest has interrupts disabled (x86_64). The VMM doesn’t park such a vCPU until the guest enables them again.

vCPUs beyond initial_active_vcpus never park

The VMM starts every vCPU so the guest can bring it online. pylond asks it to park the extra ones only once pylon-guest-agent has written its first heartbeat, and then logs VM <id>: asked <n> booted vCPU(s) to park. If that line never appears, start the agent in the guest. pylon-guest-agent --status shows the heartbeat.

A VM that parks inside KVM

Check the VMM’s log for Pylon: registered VM <id> with pylond, parking vCPUs inside KVM. If it says in the VMM instead, the VM was started with park=vmm, or on a host where that is the default (no /dev/kvm). If the line is missing, the VM didn’t register.

  • Rejected registration of VM <id>: ... needs scx_pylon in pylond’s log: pylond runs without scx_pylon. Attach it, or start the VM with --pylon park=vmm.

  • --pylon park=kvm needs KVM; use park=vmm: the VMM runs on MSHV, which has no halted state to park in.

  • woken_shared_microseconds and woken_unowned_microseconds stay at 0 under load: scx_pylon isn’t attached, so woken vCPUs run on any CPU and pylond doesn’t see them (below).

  • Pylon: failed to turn halt polling off: parked vCPUs may poll in KVM and use host CPU.

  • A parked vCPU runs while pylond shows no core for it: expected. KVM runs a parked vCPU when an interrupt arrives, and a vCPU parked by the guest or a revocation runs again after 4 ms. Its state stays parked until pylond gives it a core.

The host feels sluggish after pylond starts

scx_pylon is probably attached and scheduling every task on the host. Check cat /sys/kernel/sched_ext/root/ops. Restart pylond with --no-scx, or move host work off the managed CPUs (Kernel scheduling with scx_pylon).

Developer guide

This guide is for people who want to change Pylon: fix a bug in the arbiter, extend the shared-memory ABI, wire a new hook into the VMM, or build the guest side. It assumes you know Rust and have used KVM. It doesn’t assume you know Cloud Hypervisor’s internals or sched_ext.

To run Pylon, read the Operator guide instead. To use it, read the User guide.

Pylon from a contributor’s angle

Pylon lives in a fork of Cloud Hypervisor and is built to stay mergeable with upstream. Almost all of it is in standalone crates under pylon/. The VMM side is two files, vmm/src/pylon.rs and vmm/src/pylon_kick.rs, plus a handful of short hooks in upstream files. Four Rust crates, one BPF program and one guest kernel module make it up:

  • pylon-abi: the #![no_std] layout of the 8 KiB shared page that every other part reads and writes.
  • vmm/src/pylon.rs: creates the page, maps it into the guest, registers the VM with pylond, and parks and wakes vCPU threads. vmm/src/pylon_kick.rs is the pylon-kick PCI device, which turns pylond’s kicks into guest interrupts.
  • pylond: a two-thread daemon. A Tokio control plane on host core 0 takes registrations and requests. An allocation-free polling engine on core 1 decides, every microsecond, which vCPU owns each managed CPU.
  • scx-pylon: a sched_ext BPF scheduler and its libbpf-rs loader. It makes the kernel run each CPU’s owner, read from a memory-mapped BPF map that pylond writes.
  • pylon-guest-agent: a userspace guest daemon that reports demand. It only writes telemetry.
  • pv-pylon (pylon/guest/linux/): a Linux guest kernel module in C. It drives pylon-kick and parks a revoked vCPU at a safe point.

Repository and code organization

Upstream isolation

CMKL-APEX/pylon tracks upstream Cloud Hypervisor, and upstream changes are merged in regularly. To keep those merges cheap, Pylon follows the rule in spec/00-architecture.md §2:

  • New crates live under pylon/, where upstream never writes.
  • VMM-side logic lives in new files: vmm/src/pylon.rs, and vmm/src/pylon_kick.rs for the pylon-kick device.
  • Upstream files get only short hook calls into those files.

When you add VMM behavior, put it in vmm/src/pylon.rs (or a sibling new file) and add the smallest possible call in the upstream file.

Why two planes

The engine has to react within microseconds, so its loop must never block, allocate or take a lock that another thread can hold. Everything that can do those things (socket I/O, JSON, mmap, HTTP) runs on Plane 1. The two meet in one place: Plane 1 builds a new VM list and swaps it in with ArcSwap::store. Plane 2 loads the current list at the start of each sweep, which costs an atomic load and a reference count. Policy changes are the one exception: Plane 1 writes them straight into VmHandle’s atomic fields, and Plane 2 picks them up on its next read.

Flow: registering a VM

  1. VMM, while parsing options. PylonVmmState::new creates a memfd of 16,384 bytes (the shared page, then the host page), seals its size (F_SEAL_SHRINK, F_SEAL_GROW, F_SEAL_SEAL), maps it, zeroes it, writes both headers, and creates a kick and a wake eventfd for each vCPU slot.
  2. VMM → Plane 1, at memory setup. setup_memory_region maps the same file into guest-physical memory at gpa as a shared memory slot, and starts the pylon-session thread. Once socket exists, register_with_daemon sends one message: newline-terminated JSON (vm_id, num_vcpus, kick_signal, min_cores, max_cores, priority_weight, session, and wake_by_signal when vCPUs park inside KVM), with the file descriptors in SCM_RIGHTS in this order: the page, the kick eventfds, the wake eventfds.
  3. Plane 1. Maps the page from the descriptor, checks the header, records the VMM’s PID from SO_PEERCRED (with a pidfd, for signalling it later), builds a VmHandle, and publishes a new VM list without any old entry that has the same vm_id. It replies with {"accepted":true,"session":true,...} and a newline, and keeps the connection open as the VM’s session, outside its connection limit. The VMM waits up to 1 second for the reply and logs a rejection as a warning. When the session ends (pylond exited, or removed the VM), the VMM wakes every parked vCPU, runs the VM unmanaged, and registers it again once a new socket appears (spec 10).
  4. VMM, vCPU threads. Each thread stores its gettid() in its slot’s host_tid. The VMM tags vCPUs at or above initial_active_vcpus park_on_boot, and leaves them running so the guest can bring them online.
  5. Plane 2. Sees the VM in its next sweep.
  6. Plane 1, once a second. Lists the VM’s vCPU threads in pylon_vcpu_dom. Once the guest agent has reported (guest_heartbeat is non-zero), it sets revoke_requested on each tagged vCPU that isn’t PARKED yet and signals its thread, and the VMM parks it at its next exit.

Flow: handing a core to a VM

When a managed CPU is idle (the fast path):

  1. Guest. Reports demand: runnable_threads above the vCPUs it has, and head_wait_tsc.
  2. Plane 2, demand phase. Computes the VM’s desired cores and urgency.
  3. Plane 2, matching phase. Picks a parked vCPU of that VM (vCPUs with stranded work first), and an idle managed CPU. It writes the vCPU’s thread ID to that CPU’s owner entry, sets the slot’s assigned_pcpu, and writes the vCPU’s wake eventfd.
  4. VMM. The parked thread’s blocking read returns. It sets state = RUNNING and enters KVM_RUN. A vCPU parked inside KVM (below) can’t see the eventfd while it sleeps there, so for such a VM the engine also sends kick_signal; at the exit, the VMM finds the eventfd written and sets state = RUNNING.
  5. Kernel. With scx_pylon attached, select_cpu finds the thread in the owner table and enqueue queues it on the owned CPU with a 20 ms slice, renewed unless a task pinned to that CPU is waiting. That CPU’s SMT siblings then run only vCPUs of the same VM or nothing. Without it, the fair scheduler places the thread.

When no managed CPU is idle, the engine takes one from a donor:

  1. Plane 2, matching phase. Picks a donor vCPU on another VM (donor selection), sets its revoke_deadline_tsc to now + 8 µs and revoke_requested = 1, writes its kick eventfd, reserves the recipient vCPU, and marks the CPU Revoking.
  2. Donor. Is meant to notice, agree by writing PARKING, and exit to the VMM, which parks it and writes PARKED.
  3. Plane 2, revocation phase. Once the donor is PARKED, moves the CPU to the recipient as in the fast path. If the deadline passes first, it signals the donor’s thread with the VMM’s kick_signal until the VMM force-parks it, and gives up waiting 50 µs after the first signal (phase 2).
  4. Kernel. With scx_pylon, the recipient’s enqueue finds it owns the CPU, queues it there and kicks the CPU with SCX_KICK_PREEMPT. The kick preempts the donor thread if it still runs there, and dispatch runs the recipient.

Step 2 needs the pv-pylon module in the guest. The kick eventfd raises the vCPU’s MSI-X vector on the pylon-kick device; the module’s per-CPU park thread writes PARKING and rings the park doorbell, which exits to the VMM. Without the module, every revocation ends with step 3’s forced park. See Inside the guest.

Flow: giving a core back

When a vCPU parks while no revocation is pending, the engine’s first phase sees, on an assigned CPU, state = PARKED with revoke_requested = 0 and a higher yield_count than at assignment. It meters the time so far, clears the owner entry, sets the slot’s assigned_pcpu to unassigned, and marks the CPU Idle.

Parking inside KVM

With --pylon park=kvm, the default on KVM hosts, a vCPU parks inside KVM instead of in the VMM (spec 08). The VMM halts it and returns to KVM_RUN, which sleeps until an interrupt or a signal. An interrupt, such as the guest’s timer, runs the guest again without an exit and without a core: the vCPU stays PARKED. scx_pylon marks such a vCPU woken and runs it on a CPU its VM owns, in turns with that CPU’s owner. pylond reads the woken vCPUs, gives each a spare core (idle, or held by a VM that wants none), and counts one woken for 4 ms or longer as demand for any core of its own. After a park the guest or a revocation asked for, the VMM also makes the vCPU runnable, still PARKED, once it has been parked for 4 ms (PARK_IN_KVM_BOUND). The engine’s side is in The arbitration engine, and scx_pylon’s in The scx_pylon dispatcher.

Threads in a Pylon VMM

Pylon adds no threads to the VMM. It uses the existing vCPU threads: they park and wake themselves. A parked vCPU thread is blocked in read(2) on its wake eventfd, outside KVM_RUN, holding no locks. Inside KVM, it is instead halted in KVM_RUN, with a per-thread POSIX timer that sends SIGRTMIN when the 4 ms bound passes.

Shared-memory ABI

Every Pylon VM has one 8,192-byte shared page. The VMM, pylond and the guest all map it, and it’s the only channel between the guest and the host on the hot path. The file that backs it also holds an 8,192-byte host page after it, which only the VMM and pylond map. Its layout is defined once, in pylon/pylon-abi/src/lib.rs (#![no_std], so a guest kernel can use it too). The design is in spec/01-shared-memory-abi.md.

Rules

  • One writer per cache line, where possible. Each structure is #[repr(C, align(64))], one 64-byte cache line, so that the guest and the host don’t keep stealing the same line from each other. Each vCPU slot is split in half: the lower 32 bytes for the guest side, the upper 32 for the host side.
  • Atomics only. Every byte of the shared page, header and padding included, is an AtomicU8, AtomicU32 or AtomicU64: the guest can write any of them at any time, so the host may hold a Rust reference to the page only if nothing in it is a plain integer. No reader takes a lock.
  • Fixed size. The page is exactly two 4 KiB pages. Compile-time assertions check every structure’s size and alignment, where the header, telemetry and slots start, and the offsets of park_timer_deadline_tsc, revoke_requested, park_on_boot, host_tid and guest_tsc_offset.

ABI version 2 gave each field one writer (spec 06 §3), and version 3 keeps that. The field docs in pylon-abi say which. Version 2 has the same layout as version 1. The version changed because version-1 guest components broke these rules; a version-1 agent refuses a version-2 page, and the other way round. park_timer_deadline_tsc and guest_tsc_offset were added later in version 2, in bytes that were reserved and zero, and readers treat 0 as “not provided”, so they didn’t need a new version. park_on_boot took a reserved byte the same way.

Version 3 (spec 08 §4.4) keeps the layout too, and changes what the fields mean for a VM that parks inside KVM:

  • A PARKED vCPU may be running. An interrupt runs it without a core and without an exit, so the VMM can’t write RUNNING. Whether it runs comes from scx_pylon’s woken map.
  • The guest may write PARKING over PARKED, when its park thread saw a revocation that the VMM then forced. The VMM turns it back into PARKED.
  • park_timer_deadline_tsc only orders vCPUs. KVM fires the guest’s timer itself, so pylond uses it only to pick which vCPU of a VM gets a core first.

The wake eventfds stay: a vCPU parked inside KVM reads its own, without blocking, after each exit, to learn that pylond assigned it a core. A version-2 guest component or pylond refuses a version-3 page.

Time bases

Every *_tsc field and tsc_khz count host counter ticks: the TSC on x86_64 and the virtual counter CNTVCT_EL0 on aarch64. The names and the layout don’t depend on the architecture.

The guest writes head_wait_tsc and next_timer_tsc with its own counter. Under KVM that differs from the host’s by the vCPU’s offset (a new vCPU’s counter starts near 0). The VMM measures the offset when each vCPU thread starts, by reading the guest’s counter (IA32_TSC on x86_64, KVM_REG_ARM_TIMER_CNT on aarch64) between two host counter reads, and stores it in guest_tsc_offset. PylonSharedPage::guest_to_host_tsc subtracts vCPU 0’s offset, since KVM keeps a VM’s vCPU TSCs in sync. The conversion assumes the guest TSC runs at the host’s rate (no TSC scaling). Every other TSC field is host TSC.

Memory ordering

Writers that publish something another party acts on use Release, and the readers that act on it use Acquire. For example, pylond stores revoke_deadline_tsc and then revoke_requested = 1 with Release, so a reader that sees the flag with Acquire also sees the deadline. Counters and timestamps that are only sampled use Relaxed.

The guest’s side of that contract depends on the guest’s memory model. On x86_64, ordinary loads and stores are already ordered strongly enough for these pairs.

The page in guest memory

The VMM maps the page as a shared memory slot at PYLON_DEFAULT_GPA (0xFEDF_0000), or at --pylon gpa=. On x86_64 that address sits between the IOAPIC and the local APIC, outside the PCI windows. Like a device BAR, the page is not part of the VMM’s guest RAM (GuestMemoryMmap), so the guest’s E820 table, the PVH memory map and ACPI don’t list it. MemoryManager keeps the mapping alive for the VM’s lifetime. A guest maps it through /dev/mem, which CONFIG_STRICT_DEVMEM allows for addresses that aren’t RAM, or through /dev/pylon when the pv-pylon module is loaded. On x86_64 the /dev/mem mapping then fails, so pylon-guest-agent uses /dev/pylon when it exists.

Changing the ABI

  1. Change the spec first (spec/01-shared-memory-abi.md), and say who writes the new field.
  2. Use reserved or padding bytes, and keep every structure 64 bytes. The compile-time assertions fail otherwise.
  3. If the change alters a field’s meaning or its writer, bump PYLON_ABI_VERSION. pylond refuses pages with another version, so update the VMM, pylond and guest components together.
  4. A change to the host page needs PYLON_HOST_VERSION bumped, not PYLON_ABI_VERSION, and no guest component changes.
  5. Update every reader and writer: vmm/src/pylon.rs, pylond/src/engine.rs and lib.rs, pylon-guest-agent, the C copy of the layout in pylon/guest/linux/pv_pylon_abi.h, and the tests that build pages by hand (pylond/tests/e2e_pylon.rs, pylon_bench.rs).

The arbitration engine

pylond’s Plane 2, MatrixEngine in pylon/pylond/src/engine.rs, decides which vCPU owns each managed CPU. This page walks through one sweep. The original design is in spec/02-pylond-arbiter.md; where the code differs, this page follows the code.

The loop

#![allow(unused)]
fn main() {
// MatrixEngine::run, simplified
pin_current_thread_to_core(self.engine_cpu); // --engine-cpu, default 1
let sweep_cycles = ns_to_cycles(SWEEP_INTERVAL_NS, self.host_tsc_khz); // 333 ns
while !stop {
    let now_tsc = read_tsc();
    self.poll_once(now_tsc);
    pause_cycles(now_tsc, sweep_cycles, self.has_timed_wait);
}
}

read_tsc reads the host counter: the TSC on x86_64, CNTVCT_EL0 on aarch64 (pylon_abi::clock). pause_cycles waits until now_tsc + sweep_cycles with TPAUSE on x86_64 CPUs with WAITPKG and with WFET on aarch64 CPUs with FEAT_WFxT, and with PAUSE or a spin hint otherwise; the wait is a hint and may end early. The interval is 333 ns, so with the sweep itself a pass takes on the order of a microsecond. That figure hasn’t been measured; see Benchmarks.

Invariants of a sweep

  • No heap allocation. Per-VM demand records live in a fixed array of MAX_TRACKED_VMS = 64 entries; per-CPU state in arrays of MAX_PCPUS. At most 64 VMs are considered per sweep, in list order.
  • No locks and no blocking calls. The VM list is loaded with one ArcSwap::load. The only system calls are eventfd writes to wake or kick a vCPU, and tgkill to signal a vCPU thread (after a pidfd_send_signal check that the VMM still exists).
  • State is local. core_states (Idle, Assigned { vm_id, vcpu }, Revoking { donor…, recipient…, deadline_tsc }) is owned by the engine thread alone.

VMs that park inside KVM

A VMM started with --pylon park=kvm registers with wake_by_signal set, and parks a vCPU inside KVM instead of on its wake eventfd: the vCPU halts in KVM_RUN (spec 08 §3). An interrupt then runs the guest again without a core and without an exit; the vCPU stays PARKED. The engine treats such a VM differently in four places: a due timer is no zero-core wakeup (phase 1), vCPUs that KVM woke count as demand (phase 1), waking a vCPU for a core also takes a signal (phase 2), and it tells scx_pylon which vCPUs are parked (after phase 3).

The engine reads a vCPU’s state, yield_count, revoke_requested, revoke_deadline_tsc, assigned_pcpu, park_on_boot, host_tid and park_timer_deadline_tsc from the VM’s host page, which the guest can’t write, and writes assigned_pcpu and revocations there and to the guest’s copies. Below, those fields mean the host page’s.

Phase 0: reclaim and meter

Reclaim. For each Assigned CPU whose vCPU is PARKED with no revocation pending, and whose yield_count has gone up since the core was assigned, the vCPU gave the core up by itself. The engine meters the time since the last sample, clears the CPU’s owner entry, sets the slot’s assigned_pcpu to unassigned, and marks the CPU Idle.

The yield_count check matters because pylond doesn’t write state: a vCPU that has just been given a core stays PARKED until its thread wakes. The VMM increments yield_count before it publishes PARKED, so only a vCPU that has run and parked again is reclaimed.

Meter. For each Assigned or Revoking CPU, the engine adds the elapsed time to the owning (or donating) VM’s allocated_core_usec:

usec = (now_tsc - last_tsc) * 1000 / tsc_khz

It carries the remainder forward (it advances last_tsc by exactly the cycles it counted), so rounding doesn’t lose time across sweeps. tsc_khz is the host counter rate that pylond finds at start (calibrate_tsc_khz): CNTFRQ_EL0 on aarch64, a 50 ms measurement against the system clock on x86_64. pylond never reads the rate in a VM’s header, since the guest can write the shared page. If that fails, it assumes the architectural rate or, on x86_64, 3,000,000.

Removed VMs. A CPU still Assigned to a VM that is no longer registered (Plane 1 removes VMs whose VMM exited) is freed: the engine clears its owner entry and marks it Idle. This runs even when no VMs are left.

Phase 1: demand

For each VM, the engine counts its assigned cores (CPUs it holds) and incoming cores (CPUs being revoked for it), and reads its telemetry.

Zero-core wakeup. A VM with no committed cores qualifies if its next_timer_tsc has passed, if a free parked vCPU’s park_timer_deadline_tsc has passed, or if the host’s receive doorbell is ahead of the guest’s rx_ring_cons_idx. The two timers don’t count for a VM that parks inside KVM: KVM fires them, and the vCPU runs without a core (spec 08 §3.2). For such a VM, a vCPU that KVM woke (below) qualifies instead, once it is a long wake. A short wake runs on the shared vCPU queue: a core for it would cost another VM a forced preemption, and come back as soon as it halts.

Woken vCPUs (VMs that park inside KVM, spec 08 §4.2). The engine reads the VM’s woken mask from scx_pylon’s pylon_vm_vcpus map (by the VM’s slot; without scx_pylon, nothing writes it), keeps the vCPUs still PARKED with no core assigned, and records when it first saw each one. A vCPU woken for WOKEN_DEMAND_US (4 ms) or longer is a long wake. The longest wake counts as waiting time, like head_wait. A VM that owns a core and has no other unmet demand also wants one core per vCPU woken now (spare_only), with urgency 0, so after every other VM, and phase 3 gives it only spare cores: an idle one, or one held above its floor for at least SPARE_CORE_TENURE_US (1 s) by a VM whose desired cores are 0 (#52). Without the tenure, two idle VMs traded a spare core each time one of their vCPUs woke, as soon as the other’s agent reported no demand again: about 70 forced preemptions a second with agents reporting every millisecond.

Time bases. Every *_tsc field counts host counter ticks (the TSC, or CNTVCT_EL0 on aarch64). The guest writes head_wait_tsc and next_timer_tsc on its own counter. pylond converts them to the host counter with PylonSharedPage::guest_to_host_tsc, which subtracts the offset the VMM measured for vCPU 0. Everything else is already host TSC.

Desired cores:

Long wakes then raise desired cores to at least committed cores plus the number of long wakes, up to max_cores. That catches demand runnable_threads misses, such as work in the guest kernel or since the agent’s last report. Last, desired cores don’t drop below the cores the VM has or is getting for vCPUs that were woken when phase 3 picked them, until the guest agent reports again (guest_heartbeat moves) or WOKEN_GRANT_HOLD_US (50 ms) passes. Such a vCPU no longer counts as woken once it has its core, and runnable_threads shows its work only from the agent’s next report: its VM would otherwise give the core back in the next sweep, before the vCPU ran on it.

Phase 2: revocations in flight

For each Revoking CPU, the engine checks the donor’s slot. Only the VMM writes PARKED, once the donor’s thread has left KVM_RUN, and it increments yield_count first. The engine records the donor’s yield_count when it starts the revocation, and treats the donor as parked only when it is PARKED with a higher count. A donor that was just given its core is still PARKED from before, until its thread wakes, and that doesn’t count.

The signal is resent because one that arrives while the vCPU thread is outside KVM_RUN (handling an exit) doesn’t stop the next guest entry. It isn’t resent while the thread has left KVM_RUN since the last signal and not re-entered: the VMM counts each entry and return in the host slot’s kvm_run_seq, and acts on the request before it enters again. Each resend there would only run the signal handler again. This also holds for the signals below. The interval doubles because each signal also costs the guest an exit: a guest the VMM can’t park yet, with interrupts off, needs time in the guest to turn them back on. The 50 µs bound counts from the first signal, not the deadline, so a donor always has that long after being signalled, even when the engine runs late.

After a handoff without park, the donor still has revoke_requested set and is no longer on any Revoking CPU. Each sweep therefore also looks for such vCPUs and keeps signalling them until the VMM parks them, at an interval that grows from the deadline on, up to 1 ms. These are vCPUs with revoke_requested = 1, no assigned_pcpu, not PARKED, not tagged park_on_boot (Plane 1 signals boot parks), and a deadline that has passed. Without this, a guest that never exits to userspace on its own kept running without a core. pylond signals only a VMM that registered a kick_signal, and checks through a pidfd that the VMM process still exists before each tgkill.

Handing the CPU over unassigns the donor (assigned_pcpu), writes the recipient’s thread ID (and its VM’s slot, in the flags) to the CPU’s owner entry, sets the recipient slot’s assigned_pcpu, writes its wake eventfd, and marks the CPU Assigned to the recipient. For a VM that parks inside KVM, the wake eventfd alone doesn’t reach the thread asleep in KVM_RUN, so the engine also sends kick_signal. Each sweep sends it again, at most every REVOKE_RESIGNAL_US (10 µs), while the vCPU is still PARKED with the yield_count it had at assignment: a signal that lands just before the thread re-enters KVM_RUN interrupts nothing. When the donor parked, the time from the revocation request to PARKED goes into the VM’s park latency histogram. The engine doesn’t touch the donor’s state or revoke_requested; the VMM clears revoke_requested when it parks.

If either VM has gone, the engine drops the revocation, marks the CPU Idle, and releases the recipient’s reservation.

Phase 3: matching

The engine sorts the demand records by urgency, highest first (an in-place insertion sort over at most 64 entries). Then, for each VM in that order, while it needs more cores (desired minus committed):

  1. Pick a vCPU. The lowest set bit of stranded_work_bitmap whose vCPU is free (clearing that bit): the guest tasks queued on it can’t run until it has a core. Else the longest-woken free vCPU: it is already running, so it needs no wake-up. Else the lowest-numbered free vCPU whose parked timer is due, else the lowest-numbered free vCPU. A vCPU is free when it is PARKED and its assigned_pcpu is unassigned; a vCPU with a CPU on its way is still PARKED but already assigned or reserved. If the VM has no free vCPU, move on to the next VM.
  2. Fast path. If a managed CPU is Idle and none of its SMT siblings is another VM’s, assign it (as in phase 2’s hand-over) and continue. A CPU whose sibling the VM already holds comes first.
  3. Preemption path. Otherwise choose a donor with select_donor_pcpu, or stop matching for this VM if there’s none.

Donor selection

A CPU Assigned to another VM is an eligible donor if:

none of the CPU's SMT siblings is assigned to, or being handed to or
    from, a VM other than the recipient
and donor's vCPU isn't PARKED
and ((donor above its min_cores
        and (donor holds more than it desires
             or donor holds more than recipient's committed cores + 1
             or (donor's urgency < recipient's urgency
                 and (recipient's committed + 1) × donor's weight
                     ≤ donor's cores × recipient's weight)))
     or (recipient is a zero-core wakeup
         and recipient took no core from a donor at its min_cores
             in the last FLOOR_PREEMPT_INTERVAL_US
         and donor's urgency < recipient's urgency))

A zero-core wakeup has the highest urgency, and the timers and telemetry behind it come from the guest. So a VM woken from zero cores takes a core from a donor at its min_cores at most once every FLOOR_PREEMPT_INTERVAL_US (10 ms). A guest that parks and wakes again and again otherwise keeps taking cores below other VMs’ floor.

A PARKED vCPU on an assigned CPU either hasn’t woken since it was given the CPU, or has given it back and phase 0 will reclaim it. Revoking it would race its wakeup.

Urgency alone moves a core only while the donor keeps at least as many cores per unit of priority_weight as the recipient will have. Without that bound, two hungry VMs with equal weights traded a core on every sweep: the more urgent one took the other below an even split, then more than committed + 1 gave it back. With the bound, an even split is final, and a VM with twice the weight ends up with two cores for every one.

Among eligible donors, the engine prefers, in order:

  1. a vCPU that isn’t in a critical section;
  2. a VM holding more than it desires;
  3. the lowest urgency.

It then sets the donor slot’s revoke_deadline_tsc to now plus REVOKE_GRACE_PERIOD_US (8 µs, converted with the host’s tsc_khz), stores revoke_requested = 1, writes the donor’s kick eventfd, and marks the CPU Revoking. It reserves the recipient vCPU by setting its assigned_pcpu to that CPU, so no other match picks it. The recipient’s incoming count goes up, and the donor’s assigned count goes down, so later decisions in the same sweep see the change.

After phase 3: parked vCPUs for scx_pylon

Last, for each VM that parks inside KVM, the engine writes the mask of its vCPUs that are PARKED with no CPU assigned to the parked field of its pylon_vm_vcpus entry, and clears the entries of VMs that have gone. This runs after matching, so the vCPUs given a CPU in this sweep are already out of the mask. scx_pylon uses it to tell a parked vCPU that KVM woke from one that runs on its own CPU (The scx_pylon dispatcher).

PcpuOwnerTable is an array of { target_tid: u32, flags: u32 } indexed by host CPU. Bits 16–31 of flags hold the owner’s VM slot plus one (0 if the VM has no slot); scx_pylon finds the CPUs a VM owns by it. It lives in one of three places:

There is one PylonVmmState per VMM process, held in a process-global Mutex<Option<Arc<PylonVmmState>>> (GLOBAL_PYLON_STATE). The hooks reach it through free functions (pylon::on_vcpu_thread_start(id) and so on) that do nothing when --pylon wasn’t given. A global keeps the hooks one line each, with no new parameters threaded through upstream constructors. The cost is that a VMM process can hold only one Pylon VM. PylonVmmState is Send and Sync by unsafe impl. That’s sound because, after new finishes, the page is reached only through atomic fields and EventFds are thread-safe. Any non-atomic access added later breaks that argument.

Hooks

Configuration: parse_and_configure

Called at the end of VmConfig::parse in vmm/src/config.rs, after validation. It parses --pylon, then builds and installs PylonVmmState, creating the page. Building the state during option parsing is a side effect in an unusual place: it happens before the VM exists, and before the VMM installs its logger, so nothing logged there shows. Registration with pylond therefore waits for setup_memory_region.

The registration message carries kick_signal: SIGUSR2 (pylon::KICK_SIGNAL), for which vmm/src/cpu.rs gives vCPU threads a no-op handler, as for its own SIGRTMIN. A standard signal that is already pending isn’t queued again, so the signals pylond sends while a vCPU waits to run cost one handler, not one each. pylond sends it to a donor vCPU whose revocation deadline has passed. With park in KVM, the message also carries wake_by_signal: true (Control socket protocol). The VMM registers only if the socket exists, once per process, and waits up to 1 second for the reply. It logs where its vCPUs park when pylond accepts it, and a warning with pylond’s reason when it doesn’t; the VM then runs unmanaged. PylonVmmState::new also sets every slot’s assigned_pcpu to PCPU_UNASSIGNED, in the shared page and in the host page, which pylond reads as “no core on its way”.

Memory: setup_memory_region

Called from MemoryManager::new in vmm/src/memory_manager.rs. It wraps a clone of the shared memory memfd in a guest region at gpa and registers it with the hypervisor as a new memory slot (MemoryVisibility::Shared). It doesn’t add the region to the guest’s memory map, like a device BAR (Shared-memory ABI); MemoryManager keeps the region alive. It then registers the VM with pylond (PylonVmmState::register). With park in KVM it also turns halt polling off for the VM (KVM_CAP_HALT_POLL set to 0) and only logs a warning if that fails. Errors surface as memory_manager::Error::Pylon.

Backend check: check_hypervisor

Called from CpuManager::new. It fails VM creation with --pylon on MSHV on aarch64, which can’t read the guest’s counter and timer.

Kick device

DeviceManager adds the pylon-kick PCI device (vmm/src/pylon_kick.rs) when --pylon is given. Its MSI-X notifiers are the kick eventfds, and its BAR0 holds the park doorbell (Enhancements).

vCPU start: on_vcpu_thread_start

Called at the top of each vCPU thread in vmm/src/cpu.rs, after the thread barrier and before the first KVM_RUN. It stores gettid() in host_tid, in the host page and then in the guest’s copy, measures the guest counter offset into guest_tsc_offset (Time bases), sets RUNNING, and for vcpu_id >= initial_active_vcpus also sets the slot’s park_on_boot tag. With park in KVM it also creates the vCPU’s park bound timer. It doesn’t park those vCPUs: a guest brings its secondary CPUs online at boot (PSCI CPU_ON on aarch64, INIT/SIPI on x86_64), and a vCPU whose thread never enters KVM_RUN doesn’t answer, so the guest waits for it, gives up, and boots without it. Once the guest has booted (a non-zero guest_heartbeat), pylond sets revoke_requested on each tagged vCPU and signals its thread, and check_and_park_vcpu parks it (below).

After each exit: check_and_park_vcpu

Called in the vCPU run loop after the vCPU lock is dropped, on every exit to userspace. It applies the decision table from spec 06 §4.4 (park_decision):

To park, it clears revoke_requested, increments yield_count (and forced_preempt_count for a forced park), records last_yield_tsc, records the guest’s armed timer as park_timer_deadline_tsc, publishes PARKED with Release, blocks on the wake eventfd, and on wakeup clears park_timer_deadline_tsc and sets RUNNING again (unless shutting down). A boot park skips the counters and clears park_on_boot instead.

Under KVM with an in-kernel LAPIC, a running vCPU exits to userspace only for MMIO, PIO, signals and similar, so on its own this check runs at unpredictable times. Spec 06 adds the two exits that make it timely: the guest’s park doorbell (S4) and pylond’s signal when a deadline passes (S2).

Before S1, this hook parked on any exit while revoke_requested was set, and was also called from the VmExit::Reset arm, where KVM reports triple faults. Both are gone (Enhancements).

Shutdown: shutdown_all

Called from CpuManager::shutdown. It sets shutting_down, writes every wake eventfd, so parked threads return and see the VM is stopping, and stops the park bound timers.

    while !self.shutting_down.load(Ordering::Acquire) {
        match wake_evt.read() {           // blocking read
            Ok(_) => break,
            Err(e) if e.kind() == io::ErrorKind::Interrupted => continue,

        }
    }

}

A parked thread holds no VMM locks, so pausing, snapshotting or shutting down the VM doesn’t deadlock on it. But the VMM’s pause protocol (SIGRTMIN, vcpu_paused) doesn’t know about it either. Pausing a VM with parked vCPUs hasn’t been tested.

Parking inside KVM

With --pylon park=kvm (The –pylon option), the default on KVM hosts, a parked vCPU sleeps in KVM_RUN instead of in park_vcpu. The design and its measurements are in spec 08. The run loop passes check_and_park_vcpu a callback, kvm_park_op, that runs one KvmParkOp on the locked vCPU:

Opx86_64aarch64
InterruptsEnabledRFLAGS.IF is setAlways true: WFI wakes on a masked interrupt

Built without the kvm feature, the callback always fails.

Park. The decision table is the same. Before publishing anything, the VMM checks InterruptsEnabled and sets Halt. If either fails, the vCPU keeps running as if it hadn’t been asked, and pylond signals it again (a halted x86 vCPU with interrupts off wouldn’t wake for an IPI). Then it updates the slot as above, publishes PARKED, marks the vCPU parked in KVM, and returns. The run loop’s next KVM_RUN sleeps until an interrupt or a signal.

Wake by interrupt. KVM runs the guest again without an exit. The VMM doesn’t see it, and state stays PARKED. scx_pylon decides where the thread runs (scx_pylon).

Wake for a core. The wake eventfd can’t reach a thread in KVM_RUN, so pylond also signals the thread. After each exit of a vCPU parked in KVM, the VMM:

  1. turns PARKING back into PARKED: a guest park request that came after a forced park is already done (spec 08 §3.7);
  2. reads the non-blocking wake eventfd. If it was written, it stops the park bound, sets Run, clears park_timer_deadline_tsc and publishes RUNNING;
  3. otherwise, if the park bound has passed, it sets Run and leaves state at PARKED. The vCPU then runs without a core until it halts again.

Bound. A cooperative or forced park (not a boot park) arms a per-vCPU POSIX timer that sends SIGRTMIN to the vCPU thread after PARK_IN_KVM_BOUND (4 ms) and every 4 ms after that. It covers a vCPU that nothing would wake: no timer armed, or work queued without an IPI (spec 08 §3.6).

Halt polling is off for the VM (PARK_IN_KVM_HALT_POLL_NS = 0), so a parked vCPU costs no host CPU. This also affects the guest’s own HLT.

The scx_pylon dispatcher

scx_pylon is a sched_ext scheduler: a set of BPF callbacks that the kernel calls to decide where and when tasks run. It’s in pylon/scx-pylon, and its design is in spec/03-scx-and-vmm-hooks.md §1.

Why it exists

pylond decides in microseconds that a CPU belongs to vCPU thread T. Without scx_pylon, waking T only makes it runnable. The host’s fair scheduler then picks a CPU and a moment, with its own wakeup latency and runqueue locks. scx_pylon makes the kernel act on pylond’s decision directly, and pylond communicates that decision with memory stores, not system calls.

The maps

struct pcpu_owner_entry { __u32 target_tid; __u32 flags; };

struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 256);              // indexed by host CPU
    __uint(map_flags, BPF_F_MMAPABLE);
    __type(key, __u32);
    __type(value, struct pcpu_owner_entry);
} pylon_pcpu_owners SEC(".maps");

BPF_F_MMAPABLE lets userspace mmap the array. pylond maps it and uses it as its PcpuOwnerTable, so an owner change is two atomic stores: flags, then target_tid with Release. Bits 16–31 of flags hold the owner’s VM slot plus one (0 if unknown), so the BPF program can find the CPUs a VM owns. The HOST bit (bit 2) marks an owner that is a host thread, not a vCPU: pylond’s engine owns its CPU, so it gets the CPU first, but scx_pylon doesn’t tag it as a managed vCPU, and its SMT siblings still run host tasks. Without it, a queued vCPU thread took the engine’s CPU for a whole slice each time the engine’s slice ended (#54). The ACTIVE and PREEMPT bits are defined but not used.

Four more maps:

  • pylon_vcpu_dom (hash, by thread ID): the vCPU threads of registered VMs, with their VMM’s tgid, their VM’s slot and their vCPU index. pylond’s Plane 1 writes it.
  • pylon_vm_vcpus (array of 64 VM slots, BPF_F_MMAPABLE): two vCPU bitmasks per VM, parked and woken (spec 08 §4.3). pylond’s engine writes parked, the vCPUs that are PARKED with no CPU assigned. scx_pylon writes woken, the parked vCPUs that KVM woke and that are runnable. pylond maps it.
  • pylon_smt_next (array): the SMT sibling ring, described below.
  • pylon_guard: state of the core scheduling guard, described below.

Callbacks

select_cpu(p, prev_cpu, wake_flags), when a task wakes:

  1. If prev_cpu’s owner is p, return prev_cpu.
  2. Otherwise scan all 256 entries for one owned by p, and return that CPU if found.
  3. Otherwise use scx_bpf_select_cpu_dfl, the default placement.

A task found as an owner is marked in task-local storage with its VMM process’s tgid: its domain. A vCPU thread gets its domain earlier, at its first enqueue, when pylond has listed it in pylon_vcpu_dom. pylond‘s control plane keeps that map in line with the registered VMs’ shared pages every second. enqueue checks the tgid too, so a thread ID reused by another process isn’t tagged. A vCPU is therefore isolated whether or not it ever owns a CPU, which matters because pylond only gives CPUs to vCPUs that are parked (initial_active_vcpus: the vCPUs beyond it are parked once the guest has booted).

enqueue(p, enq_flags) puts each task on one of these queues:

  • The owner of its CPU goes on that CPU’s owner queue (DSQ id = CPU) with a 20 ms slice, and the CPU is kicked with SCX_KICK_PREEMPT (not when that CPU is just putting p back after running it). This is what preempts a donor whose CPU was given to a recipient.
  • A parked vCPU that KVM woke goes on its VM’s queue (PYLON_VM_DSQ + slot) with a 100 µs slice, if its VM owns a CPU it may run on, and that CPU is kicked. If its VM owns none, it goes on the vCPU queue instead. This applies to VMs that park inside KVM (--pylon park=kvm, spec 08). enqueue recognises such a vCPU by its bit in parked, and sets its bit in woken. The bit is cleared when the vCPU is enqueued as an owner, and by quiescent when it stops being runnable.
  • Another vCPU thread with a domain goes on the vCPU queue. If it owns a CPU elsewhere, that CPU is kicked.
  • A host task allowed on only one CPU, such as a per-CPU kworker, goes on that CPU’s local queue, and that CPU is kicked if it is idle.
  • Everything else goes on the host queue.

A task with migration disabled stays on its CPU’s local queue too. The kernel runs a CPU’s local queue before it asks dispatch for work, so when the owner’s slice ends, a pinned task waiting there runs first. The owner then gets the CPU back. With SCX_ENQ_LAST, the CPU has already decided to idle with p runnable, so enqueue kicks it to schedule again.

dispatch(cpu, prev), when a CPU needs work, tries in order:

  1. The CPU’s owner queue. Tasks that no longer own the CPU are moved to the vCPU or host queue. An owner whose slice just ended is still prev, not on the queue; it keeps the CPU for another slice.
    • pylond can give the CPU to a vCPU thread that already waits on the vCPU queue or on its VM’s queue. enqueue doesn’t run again for a queued thread, so dispatch also looks for the owner on those two queues.
    • While woken vCPUs wait on the queue of the owner’s VM, the owner and they take 100 µs turns (the owner’s slice is 100 µs instead of 20 ms while they wait). The owner entry’s flags carry the VM’s slot. running records, per CPU, the thread ID of the owner if it ran last, or that a woken vCPU did; host tasks that run between turns, such as per-CPU kworkers, don’t change it. A woken vCPU’s turn comes only while that thread still owns the CPU, so a new owner runs first. pylond often gives a CPU to one of the woken vCPUs, and before this, the turn left by the old owner went to a sibling of the new owner, which then waited up to a tick (#54).
  2. The vCPU queue, skipping threads that own another CPU. Such a thread’s CPU is kicked if it is idle, in case it got the CPU while it waited here.
  3. The host queue.

Each dispatch also checks one VM queue in turn (rescue_stranded_vcpus). If that VM no longer owns a CPU, its vCPUs move to the vCPU queue, so they don’t wait until the stall watchdog fires. An idle CPU is kicked for each, because idle CPUs only look at the vCPU queue when kicked.

Each step only dispatches what the SMT claims allow. If nothing fits, the CPU idles.

SMT isolation

Kernel core scheduling (PR_SCHED_CORE) can’t be used with sched_ext on kernels that lack the upstream fixes for 4c95380701f5 (issue #15). So scx_pylon does the job itself for managed vCPU threads: while a CPU runs a vCPU of VM A, its SMT siblings run only vCPUs of A or nothing.

Each CPU publishes a claim in cpu_claim[]: idle, host, pinned (a host task allowed on only that CPU), or a domain (tgid).

  • dispatch publishes the claim before checking the siblings. Two siblings claiming at once each see the other’s claim.
  • running records the task actually running, and update_idle clears the claim.
  • running also checks the siblings again. A sibling can claim after dispatch checked, and its kick can land before the new task is current, preempting nothing. The task would then run a whole slice next to the sibling, so the CPU kicks itself instead. Tasks with migration disabled skip this: they go back on the same CPU.
  • The order is: a domain beats host, and between two domains the lower-numbered CPU wins. The winner kicks the loser with SCX_KICK_PREEMPT, and the loser’s next dispatch backs off.
  • A pinned task can’t go anywhere else, so it runs without checking its siblings. Instead, a domain yields to it, and running kicks the siblings whose domain claims yield when a pinned task starts. The exception is a CPU’s owner: it doesn’t yield, or a busy pinned task next to it would keep it waiting until the watchdog fired.
  • When a domain or pinned claim ends, the siblings are kicked to look for work again.

The siblings come from pylon_smt_next, a ring (next CPU on the same core) that load_and_attach() fills from /sys/devices/system/cpu/cpu<N>/topology/thread_siblings_list before attaching. When scx_pylon is attached, pylond gives the engine the same ring. It then never assigns two VMs sibling threads of one core, and prefers the free thread of a core the VM already holds.

Not isolated:

  • tasks of higher sched classes (RT, deadline, stop);
  • interrupts and softirqs;
  • tasks with migration disabled, which are short and pinned;
  • host tasks allowed on only one CPU, mostly per-CPU kernel threads, when they run on an owned CPU or next to its owner. They can’t wait for the owner to block: a busy vCPU may never block, and the kernel’s watchdog would eject the scheduler.

Kernel core scheduling doesn’t isolate interrupts either.

Core scheduling guard

Kernel core scheduling turns on for the whole host as soon as any task has a cookie, for example a stock Cloud Hypervisor VM, which asks for one by default (core_scheduling=vm). On kernels without upstream f2da9587118d and d954004205c1, sched_ext then corrupts the core-scheduling pick, which ends in a NULL dereference in pick_next_task() or a hard hang (issue #15). The guard keeps scx_pylon from running while any cookie exists. It lives in src/coresched.rs and two more BPF programs:

  • KernelCoreSched::detect() decides whether the kernel needs it. PR_SCHED_CORE_GET fails with EINVAL without CONFIG_SCHED_CORE and with ENODEV without SMT. Otherwise the kernel has the fix if its BTF has struct scx_rq member lock_drop_seq, which f2da9587118d adds and d954004205c1 depends on.
  • pylon_task_prctl (lsm/task_prctl) refuses every PR_SCHED_CORE command except GET. It reads its answer, EPERM or ENODEV, from the pylon_guard map. task_prctl programs run as modify-return, so returning 0 lets the prctl go on as usual.
  • pylon_sched_core_get (fentry/sched_core_get) records the tgid of a task that gets a new cookie anyway. dispatch then calls scx_bpf_exit() once with that pid, and the kernel falls back to the fair scheduler.

load_and_attach(Some(deny)) attaches the LSM program and the watcher first, then checks every thread with PR_SCHED_CORE_GET, and only then attaches the scheduler. Both programs are left out of the load without the guard (and the LSM program with CookieDenial::Off), since kernels without CONFIG_SCHED_CORE have no sched_core_get().

The flags are SCX_OPS_ENQ_LAST, SCX_OPS_ENQ_EXITING, SCX_OPS_ENQ_MIGRATION_DISABLED and SCX_OPS_KEEP_BUILTIN_IDLE.

Costs and open points

  • The scan in select_cpu is up to 256 map lookups for every wakeup of every task on the host that isn’t on its owned CPU, including tasks that own nothing. A reverse map (thread ID to CPU) would make it one lookup.
  • An owner gives up its CPU only to tasks that can run nowhere else, for at most one slice each (20 ms). A busy task pinned to an owned CPU therefore halves the owner’s time. A task that can run on two CPUs, both owned or fenced, still waits until a vCPU blocks, and the stall watchdog can eject the scheduler.
  • The program is attached for the whole host (.name = "pylon", no partial-switch flag), so every SCHED_NORMAL task goes through it.
  • Two VMs on sibling threads (only possible without pylond’s placement, for example with VMs it doesn’t manage) take turns badly: the lower-numbered CPU’s VM wins for as long as its vCPU runs.

None of these has been measured yet.

Design decisions and trade-offs

This page explains why Pylon is built the way it is. For each choice a contributor is likely to question, it gives the decision, the reason, what it costs, and when to look at it again. The reasons come from the specs (spec/00-architecture.md to 08) and from pull requests. Where the project hasn’t written a reason down, this page says so.

To change a decision, change the spec that records it first, in its own pull request or as the first commit of one, then the code (Contributing).

The goal: space-sharing, not time-sharing

Decision. A managed host CPU runs at most one vCPU at a time. The host never time-slices two runnable vCPUs on one CPU. Instead, the guest schedules its threads onto the vCPUs it currently has, and the host moves whole CPUs between VMs (spec 00 §1, invariants 1 and 2).

Why. Time-slicing vCPUs gives the guest scheduling on two levels that don’t know about each other (the “double-scheduling tax”). It also preempts vCPUs that hold guest locks, which stalls every other vCPU spinning on that lock. Space-sharing removes both, if CPUs can be moved fast enough to follow demand.

Cost. Every other decision on this page exists to make CPU moves fast and safe. A guest that doesn’t report demand gets no elasticity.

Park vCPU threads instead of hotplugging vCPUs

Decision. All vCPUs exist and are online in the guest from boot. Pylon “removes” one by blocking its host thread on an eventfd.

Why. ACPI CPU hotplug goes through firmware notification and the guest’s CPU online/offline path, which takes milliseconds per CPU (see Benchmarks for the modelled comparison). Blocking and waking a thread takes microseconds and needs nothing from the guest.

Cost. The guest doesn’t know a vCPU is parked. Work it queues there, and interrupts it sends there (TLB shootdowns, reschedule IPIs), wait until pylond wakes the vCPU (spec 06 open question Q2). Spec 08 answers this for unmodified guests: with --pylon park=kvm, the VMM parks the vCPU halted inside KVM instead of on the eventfd, so an interrupt wakes it, and scx_pylon runs it on its own VM’s CPUs. Its measurements (spec 08 §7.4) made it the default on x86_64 KVM hosts, and spec 07 A-T8 on aarch64 (Enhancements).

Revisit once spec 08’s measurements (P3) show whether parking inside KVM should replace the eventfd park.

Shared memory on the hot path

Decision. Demand, revocation requests, vCPU state and CPU ownership all pass through shared memory: the per-VM page and the BPF owner map. The socket is used only for registration, policy and stats.

Why. A system call costs about a microsecond with today’s mitigations. A handoff budget of a few microseconds (spec 00 invariant 3: “~3–6 µs core handoff”) leaves no room for several of them.

Cost. Every field needs an ownership and ordering rule, and the ABI is versioned and hard to change (Shared-memory ABI). The rules weren’t strict enough at first (spec 06 P6).

A polling arbiter on a dedicated core

Decision. pylond’s engine spins on one host CPU (core 1 by default), sweeping every VM’s page about every microsecond, and waits between sweeps with TPAUSE on x86_64 or WFET on aarch64 (spec 02 §1, spec 07).

Why. Interrupt- or event-driven designs put a wakeup, which costs microseconds, on the path of every decision. Polling sees a change within one sweep.

Cost. One host core is permanently busy, and a second (core 0) runs the control plane. On a small host that’s a large share. Sweep time grows with the number of VMs (up to 64 per sweep).

Revisit if hosts are small, or if UMONITOR/UMWAIT on the telemetry lines can replace polling (the earlier docs/pylon.md mentioned them; the code doesn’t use them).

Two planes joined by ArcSwap

Decision. Everything that can block (socket I/O, JSON, mmap, HTTP) runs on Plane 1. Plane 2 sees the VM list only through ArcSwap<Vec<VmHandle>> (spec 02 §1).

Why. It keeps the engine free of locks, allocation and blocking without making Plane 1’s code unusual.

Cost. Registering or removing a VM copies the whole list. That’s fine at tens of VMs per host.

Cooperative revocation with a hard deadline

Decision. pylond asks a donor to yield and waits up to 8 µs (REVOKE_GRACE_PERIOD_US). After that, it takes the CPU anyway.

Why. Asking lets the guest finish a critical section first, so the revocation itself doesn’t cause lock-holder preemption. The deadline bounds how long a recipient can wait for an uncooperative or broken guest. The project hasn’t recorded why 8 µs specifically. It matches the “~3–6 µs” handoff target plus margin.

Cost. It needs a guest-side path to be cooperative at all. The pv-pylon module provides one, but a kick takes about 20 µs to reach PARKED, longer than the 8 µs grace, so many revocations still end in a forced park (Enhancements).

sched_ext for the kernel side

Decision. A BPF sched_ext scheduler runs each CPU’s owner, reading pylond’s decisions from a memory-mapped map (spec 03 §1).

Why. It’s the only way to change scheduling decisions in a stock kernel without a kernel module or patch, and the map makes each decision a memory store.

Cost. sched_ext replaces the scheduler for the whole host while it’s attached, not only for vCPU threads. It needs Linux 6.12 or later. pylond therefore treats it as optional: it attaches it when it can and runs without it otherwise (#9). Parking inside KVM (spec 08) is the exception: it needs scx_pylon to keep woken vCPUs on their VM’s CPUs.

A fixed guest-physical address

Decision. The page is a RAM slot at 0xFEDF_0000, not a device.

Why. It needs no device model, and a guest can find it with no discovery protocol. The reason isn’t recorded beyond simplicity.

Cost. The address is fixed. Pylon declares it in both arch layouts (PYLON_SHARED_START, in the 32-bit reserved hole), but a future upstream device could still want it. The page has its own memory slot but isn’t guest RAM, so it stays out of the guest’s E820 table (it used to be listed as RAM). The pylon-kick device reports the address in BAR0, and spec 06 §9 plans to move the page into a BAR (#59).

Isolate from upstream

Decision. New crates under pylon/, VMM logic in new files (vmm/src/pylon.rs and vmm/src/pylon_kick.rs), and short hooks in upstream files (spec 00 §2, spec 04 §1).

Why. Upstream Cloud Hypervisor changes quickly. Every line Pylon changes in an upstream file is a possible conflict at each merge.

Cost. The VMM side reaches its state through a process-global instead of passing it explicitly, and VMM features that need more than a hook still need a small upstream touch: the pylon-kick device is created from device_manager.rs, and park inside KVM added Vm::set_halt_poll_ns to the hypervisor crate (Organization).

JSON over a Unix socket, with SCM_RIGHTS

Decision. The control protocol is one JSON object per connection, with file descriptors attached as SCM_RIGHTS.

Why. It’s off the hot path, easy to drive from a shell or from Glidex, and passing descriptors lets pylond map pages and signal eventfds without access to the VMM’s files. The project hasn’t recorded why it chose JSON over a binary format; human readability is the likely reason.

Cost. Message types are told apart by trial parsing (Control socket protocol), and there is no authentication beyond socket permissions.

A no_std ABI crate

Decision. pylon-abi is #![no_std] with no dependencies.

Why. The same types must compile into a guest kernel module or a Rust guest kernel (spec 00 names Asterinas ostd), not only into userspace.

Cost. The Linux module pv-pylon is C, so it can’t use the crate. It repeats the layout in pv_pylon_abi.h, with static assertions on the same offsets.

A userspace guest agent first

Decision. The first guest component is a userspace daemon that reads /proc.

Why. It works with an unmodified guest kernel and was quick to build.

Cost. It reports demand milliseconds late, can’t see critical sections and can’t act on revocations. Its early attempt to act on them was wrong (spec 06 P4). Since spec 06 S3 it is telemetry-only, and cooperation moved into the pv-pylon kernel module (S5).

Problems in the original revocation path

The handoff in Architecture expects the donor vCPU to be interrupted, finish any critical section, and park. Six problems prevented that. Spec 06 steps S1–S4 fixed all six (spec 05, “Known Issues”):

Kick delivery: the pylon-kick PCI device

A small virtual PCI device, created with --pylon, with one MSI-X vector per vCPU (spec 06 §4.2). The guest driver pins vector i to CPU i, so vector i interrupts vCPU i. The device installs the VMM’s kick eventfds, the ones pylond already has, as its MSI-X notifiers, so a write from pylond goes through the irqfd path and arrives as an interrupt. BAR0 exposes the magic, ABI version, vCPU count and the shared page’s address, plus a park doorbell; BAR1 holds the MSI-X table.

Implemented (S4) in vmm/src/pylon_kick.rs, as 1af4:10f0 (Q1). While the guest hasn’t enabled a vector, or has masked it, a kick waits in its eventfd and is delivered once the vector is enabled. A VM with --pylon now refuses to snapshot or migrate. The guest driver is pv-pylon (S5).

Alternatives the spec rejected: a raw vector chosen by the guest (Linux has no supported way for a module to own one), KVM_SIGNAL_MSI from pylond (it doesn’t hold the VM’s descriptor), ivshmem-doorbell (Cloud Hypervisor implements only ivshmem-plain), and a virtio device (too heavy for one doorbell and N interrupts).

Cooperative park: a doorbell, then a decision table

At a safe point, the guest writes state = PARKING and then any value to the PARK_DOORBELL register. That MMIO write exits to the VMM on the writing vCPU, so the vCPU runs no more guest code. The device’s handler does nothing (it must not block while holding the device’s lock). The existing post-exit hook decides (spec 06 §4.4):

staterevoke_requestedDeadlineAction
PARKINGanyanyCooperative park. A park without a revocation (an idle guest giving a core back) is allowed.
RUNNING1passedForced park; forced_preempt_count += 1.
RUNNING1not passedReturn: the guest hasn’t agreed and still has time.
RUNNING0—Return (the common case: one atomic load).

The VmExit::Reset hook was removed (S1).

Forced park: a signal from pylond

Implemented (S2). When a deadline passes, pylond sends tgkill(vmm_pid, host_tid, kick_signal) (spec 06 §4.4–4.5). Cloud Hypervisor’s vCPU threads already ignore SIGRTMIN with a no-op handler, and the VMM gives them the same handler for kick_signal, so KVM_RUN returns EINTR, the KVM backend reports VmExit::Ignore, and the post-exit hook force-parks. Details:

  • The VMM sends SIGUSR2 as kick_signal when it registers. Unlike a real-time signal, it doesn’t queue, so signals sent while a vCPU waits to run cost one handler. pylond accepts SIGUSR1, SIGUSR2 or a real-time signal, and doesn’t signal a VMM that sent none.
  • pylond learns the VMM’s PID from SO_PEERCRED and opens a pidfd for it. Before each signal it checks the process still exists, so a reused PID is never signalled.
  • The signal is resent, because one that arrives while the thread is outside KVM_RUN doesn’t stop the next guest entry. The interval starts at 10 µs and doubles with each signal, up to 1 ms. A thread that has left KVM_RUN since the last signal isn’t signalled again until it re-enters (kvm_run_seq).
  • pylond hands the CPU over only once the VMM has written PARKED. As a last resort it hands it over 50 µs after the deadline, counted separately as a handoff without park.
  • pylond no longer writes WAKING. It reserves a recipient through assigned_pcpu and reclaims a core only after the vCPU’s yield_count has moved (The arbitration engine).

The guest kernel module

pv-pylon (pylon/guest/linux/, spec 06 §4.6) binds to the device, maps the page, and allocates one MSI-X vector per vCPU.

  • Vectors. Vector i is pinned to CPU i whenever that CPU comes online. The kernel’s managed spreading isn’t used, because it doesn’t keep that order.
  • The kick. The kick handler wakes CPU i’s SCHED_FIFO park thread. A kick that lands on another CPU is forwarded to that thread, not dropped.
  • The park. The thread runs at a safe point. It sets the vCPU’s stranded_work_bitmap bit if other tasks are waiting, writes state = PARKING, then writes the doorbell. The vCPU stops at that write until pylond wakes it.
  • /dev/pylon. The module exposes the page there, and pylon-guest-agent maps it instead of /dev/mem. The agent has been telemetry-only since S3.

Still to do: keeping in_critical_section up to date, and making other vCPUs treat parked ones as preempted. Neither can be done from a module; both need guest kernel changes (spec 06 Q3, #56).

Parking inside KVM (spec 08)

A vCPU parked on its wake eventfd blocks in the VMM, outside KVM_RUN. Interrupts sent to it wait until pylond gives it a core, and the guest can’t tell it isn’t running. In a two-VM run on 2026-10-31 this led to soft lockups and RCU stalls within 30 s (spec 08 §1). Spec 08 parks the vCPU inside KVM instead, so KVM wakes it like a vCPU the guest halted itself. It needs no guest changes.

The VMM uses it with --pylon park=kvm, the default on x86_64 KVM hosts, and only on KVM. It relies on scx_pylon: pylond without it rejects such a VM (spec 08 §2). How it works:

  • Park. The VMM takes the usual steps up to PARKED, then sets the vCPU halted (KVM_MP_STATE_HALTED on x86_64, KVM_MP_STATE_SUSPENDED on aarch64) and calls KVM_RUN again. KVM sleeps the thread. Halt polling is off for the VM (Vm::set_halt_poll_ns(0)).
  • Wake by interrupt. An IPI, the guest’s timer or a device MSI wakes the vCPU inside KVM. The VMM and pylond don’t see this. The vCPU stays PARKED and runs without a core of its own.
  • Wake for a core. pylond signals the thread, as for a forced park. KVM_RUN returns EINTR, and the VMM sees assigned_pcpu, sets the vCPU runnable and writes RUNNING.
  • Interrupts off (x86_64). At a forced park the VMM checks RFLAGS.IF. If interrupts are off it doesn’t park, and pylond signals again later.
  • Bounded park. A parked vCPU that nothing wakes runs again after 4 ms (PARK_IN_KVM_BOUND), still without a core. A boot park has no bound.
  • scx_pylon. The engine publishes which vCPUs are parked in the pylon_vm_vcpus map, and scx_pylon marks those it sees runnable as woken. A woken vCPU shares its own VM’s CPUs in short turns. If its VM owns none, it runs on the shared vCPU queue.
  • pylond. It reads the woken bits each sweep. A vCPU woken for longer than 4 ms (WOKEN_DEMAND_US) counts as demand for a core, and a VM with no core gets a zero-core wakeup then. A shorter wake, in a VM that owns a core, takes only a spare core: an idle one, or one held for at least 1 s by a VM that wants none. A core given to a woken vCPU stays wanted until the guest agent reports again, or for 50 ms (WOKEN_GRANT_HOLD_US). Woken time is metered per VM (woken_shared_usec, woken_unowned_usec).

  • Q4. Whether MSHV reports a signal-interrupted run the way KVM does (#65).

Performance and benchmarks

This page collects Pylon’s performance figures: what was run, where, when and how, and how to run it again. There are few so far. A core handoff between real VMs takes about 100–125 µs at the median, against a 3–6 µs target: see Handoff latency between real VMs.

How to read the numbers

  • Every result is from one date on one machine. It is a data point, not a guarantee.
  • Modelled figures come from a program that imitates part of the system. They show what the model predicts, not what a VM sees.
  • Defaults and limits (the 8 µs grace period, the 1,000-cycle pause) are configuration, not measurements.

pylon-bench: Pylon parking vs. modelled ACPI hotplug

pylon-bench (pylon/pylond/src/bin/pylon_bench.rs) runs the same CPU-bound workload twice, scaling between 1 and 8 workers in bursts:

  • Pylon: worker threads stand in for vCPUs. They park and wake through a real shared page, a real MatrixEngine and eventfds, exactly as vCPU threads would, but no VM or KVM is involved.
  • ACPI hotplug: a model of Cloud Hypervisor’s hotplug path (thread creation, a barrier, the _SB_.PRES register scan) plus fixed guest-side delays it injects: 2,500 µs to bring a CPU online and 1,500 µs to take one offline, by default (--acpi-bringup-us, --acpi-eject-us). Those delays aren’t measured. They are estimates of the guest’s CPU hotplug path, and they dominate the ACPI column.

pylond exits on SIGTERM or SIGINT (default signal handling), or when the control plane fails, for example if it can’t bind the socket. scx_pylon, if attached, is detached by the kernel when the process exits.

Control socket protocol

pylond listens on a Unix stream socket (--socket, default /run/pylon/pylond.sock). Each connection carries one request and one response: the client sends one JSON object in a single sendmsg, optionally with file descriptors attached as SCM_RIGHTS, and pylond replies with one JSON object.

Anyone who can write to the socket can register a VM. pylond records the registering peer’s UID (SO_PEERCRED): stats and policy updates cover only the VMs that UID registered, unless the caller is root or runs as pylond’s own UID, who see and manage every VM (Running pylond).

Telling messages apart

Messages have no type field. pylond decides in this order:

  1. File descriptors attached: a registration.
  2. An action of "stats", "metrics" or "status": a stats request.
  3. Otherwise: a policy update.

A message meant as a stats request with a misspelled action is therefore treated as a policy update. Because it has no vm_id, it’s rejected with {"accepted": false, "message": "invalid control request: ..."}.

Registration

Sent by the VMM at start. You don’t send this by hand.

{"vm_id": 17, "num_vcpus": 8, "min_cores": 1, "max_cores": 8, "priority_weight": 100, "kick_signal": 34}

kick_signal (optional) is the signal that interrupts a vCPU’s KVM_RUN in the VMM: SIGUSR2 (12 on x86_64 and aarch64) from the Pylon VMM, which sent its SIGRTMIN up to v0.0.8-rc3. pylond sends it to a donor vCPU’s thread when a revocation’s deadline passes. It must be SIGUSR1, SIGUSR2 or a real-time signal. Without it, pylond never signals the VMM. pylond takes the VMM’s PID from the socket’s peer credentials, not from the message.

wake_by_signal (optional, default false) is sent as true by a VMM that parks vCPUs inside KVM (--pylon park=kvm, spec 08). The wake eventfd can’t reach a thread blocked in KVM_RUN, so pylond also sends kick_signal when it assigns a core, and again until the vCPU leaves PARKED. The VMM leaves the field out when it’s false. pylond rejects such a registration when scx_pylon isn’t attached: without it, a woken vCPU would run on any CPU.

Attached descriptors, in order: the shared page’s file, then num_vcpus kick eventfds, then num_vcpus wake eventfds (1 + 2 × num_vcpus in all).

pylond maps the shared page’s file and writes the eventfds, so it checks them first. The file must be a memfd on shmem whose size is sealed (F_SEAL_SHRINK and F_SEAL_GROW): one that could shrink would make pylond crash with SIGBUS when it next reads the page. Each kick and wake descriptor must be an eventfd. A registrant still shares those eventfds and could make a write to one block, so a watchdog thread interrupts any write that blocks for 1 ms (with SIGUSR1); pylond then stops writing to that VM’s descriptors and drops its registration.
