Pylon

Performance and benchmarks

This page collects Pylon’s performance figures: what was run, where, when and how, and how to run it again. There are few so far. A core handoff between real VMs takes about 100–125 µs at the median, against a 3–6 µs target: see Handoff latency between real VMs. For AI agents on GPUs, how many cores a VM gets matters far more than how fast they move: see Agentic inference and fine-tuning on GPUs.

How to read the numbers

  • Every result is from one date on one machine. It is a data point, not a guarantee.
  • Modelled figures come from a program that imitates part of the system. They show what the model predicts, not what a VM sees.
  • Defaults and limits (the 8 µs grace period, the 1,000-cycle pause) are configuration, not measurements.
  • In every real-guest run before 2026-11-15, each VM’s boot vCPU (initial_active_vcpus) ran outside the managed cores, on host CPUs pylond doesn’t manage, for the VM’s whole life. A busy VM used one more CPU than its cores: two busy 4-vCPU VMs on three managed CPUs used 5. Comparisons between Pylon builds are still like for like; comparisons with a baseline pinned to the managed cores aren’t. From then on, a VM’s first core goes to that vCPU.

pylon-bench: Pylon parking vs. modelled ACPI hotplug

pylon-bench (pylon/pylond/src/bin/pylon_bench.rs) runs the same CPU-bound workload twice, scaling between 1 and 8 workers in bursts:

  • Pylon: worker threads stand in for vCPUs. They park and wake through a real shared page, a real MatrixEngine and eventfds, exactly as vCPU threads would, but no VM or KVM is involved.
  • ACPI hotplug: a model of Cloud Hypervisor’s hotplug path (thread creation, a barrier, the _SB_.PRES register scan) plus fixed guest-side delays it injects: 2,500 µs to bring a CPU online and 1,500 µs to take one offline, by default (--acpi-bringup-us, --acpi-eject-us). Those delays aren’t measured. They are estimates of the guest’s CPU hotplug path, and they dominate the ACPI column.

What it does and doesn’t show. The Pylon column is the time to wake and park threads through the real engine and eventfds on a busy host. Pylon’s latency budget is a few microseconds, and 138 µs is far above it. The reason hasn’t been investigated (#54): thread scheduling without scx_pylon assignments for these worker threads, the engine sharing CPUs with the workload, and the benchmark’s own polling are all candidates. The ACPI column is mostly the injected delays, so the ratio between the columns follows from the model’s assumptions. Don’t quote it as a measured speed-up.

What it does and doesn’t show. Pylon’s scale-out is about 6× and its scale-in about 17× faster than on 2026-10-29. scx_pylon’s cost to the benchmark (modelled, 2026-10-30 and 2026-11-02)

scx_pylon makes the Pylon column slower. The benchmark’s worker threads aren’t vCPUs, so to scx_pylon they are host tasks, and each wake of one goes through scx_pylon’s host path: enqueue, the shared host queue, then dispatch with its claim checks. Without sched_ext the kernel wakes them directly.

On the EPYC 9124 host (2026-10-30). One pylon-bench build from main, with sched_ext off or with scx_pylon from one of two commits attached by a test pylond. Means, rounded. The raw results were lost when the host restarted, so only these figures remain.

ConfigurationScale-out, meanScale-in, mean
sched_ext off, with or without pylondabout 20 µsabout 2.5 µs
scx_pylon at e679f1133 (the 2026-10-29 build)about 55 µsabout 12 µs
scx_pylon at main then (after #16, #17 and #21)about 65 µsabout 24 µs

Most of the cost is scx_pylon itself. The rest came with #16, which sent every waking host thread through the host queue and dispatch; before it, the kernel’s global queue took them without calling into BPF. Earlier runs that day were 4 to 5 times slower in every configuration, sched_ext off too, because of other load on the host.

A fast path, tried in the dev VM (2026-11-02). The change: in select_cpu, a host task that wakes onto an idle CPU whose siblings allow host work is inserted on that CPU’s local queue, skipping the host queue and dispatch. Six interleaved rounds of pylon-bench (defaults) in a 16-vCPU KVM guest on the same host (kernel 7.0.0-38-generic), one bench build, scx_pylon attached by a test pylond (--cores 2-5). Medians of the six runs:

The fast path didn’t help. Its scale-out was slower in five of the six rounds and about the same in the other; its scale-in was faster in some rounds and much slower in others. It wasn’t merged. A likely reason is that a task inserted this way runs a default 20 ms slice on a CPU that another task may want soon. The guest’s own vCPUs halt and wake through the host, so every figure here is noisier and higher than on the host itself: single runs of sched_ext off reached 252 µs out and 155 µs in. Read the table for its order, not its values.

Not known yet: the cost for a real vCPU, which scx_pylon places directly instead of through the host queue. These threads are a proxy for host tasks, which is the open gap below.

What it shows:

  • Parking inside KVM keeps an unmodified guest at the baseline’s throughput, with no stall in 22 runs. Parking in the VMM strands the guest’s tasks on parked vCPUs: throughput falls by a third to two thirds, the ping-pong never runs, and with the other VM busy VM 1 stops. This is why park=kvm is the default on aarch64 as well.
  • Idle-state exits are most of a wake’s latency on this host. Holding the cores out of deep idle cuts the forced-park wake’s p99 from 531 to 732 µs to 11 to 12 µs, and the baseline ping-pong from 224 / 512 to 10 / 12 µs.
  • With the other VM busy and the cores held out of deep idle, the ping-pong’s p99 rises to about 1.1 ms, against about 0.1 ms without the hold. Not explained yet; it may be the same kind of tail as the x86_64 ~1.9 ms tail (#52).
  • The engine’s core type (X925 or A725) made no measurable difference.
  • VM 1’s VMM used 32 to 41% of a CPU with park=kvm, against 27% for the baseline.

Handoff latency between real VMs (measured, 2026-11-13)

Spec 06 step S6 (#53), from pylond’s latency histograms (Metrics).

Setup: a bare-metal x86_64 host (AMD EPYC 7282, 16 cores with SMT, Ubuntu 7.0.0-43 kernel), pylond with scx_pylon on 3 managed CPUs. Two 4-vCPU Ubuntu guests park inside KVM (the default) and load pv-pylon. VM 1 runs the spec 06 S5 load (two spinners and a /proc reader on every CPU); VM 2 spins on 3 vCPUs for 100 ms every second, so cores move about 200 times each way per run. 150 s runs, the first 40 s dropped, two runs each; percentiles are read from the buckets. The default grace (8 µs) makes every revocation forced; a 200 µs grace (--revoke-grace-us 200) makes them cooperative.

Interval, µs (p50 / p99)Grace 8 µs (forced)Grace 200 µs (cooperative)
Revocation request → donor PARKED55–67 / 64–72 (a few per run: most donors hadn’t parked 50 µs after the signal)66–82 / 79–153
Core assigned → recipient running38–48 / 57–14042–47 / 59–78
Revocation request → recipient running100–112 / 117–205114–126 / 137–291

These are with the re-signal back-off below. The target is a handoff in 3–6 µs and a park within the 8 µs grace; both are an order of magnitude off.

Where the time goes (from a host trace of signals, KVM exits and system calls):

  • The signal stops the vCPU’s KVM_RUN within 3–6 µs.
  • The VMM then takes 40–60 µs before it publishes PARKED (forced park) or re-enters the guest (wake). About 17 µs of it pass before the first signal handler returns; most of that is the trace’s own probes (see the profile below).
  • pylond re-signalled a waking vCPU every 10 µs, so several signals were delivered during one wake. Backing the re-signals off from 100 µs cut wake p50 from 53–58 to 42–46 µs and p99 from 88–124 to 59–78 µs.
  • The VMM’s seccomp filter costs 5–10% (--seccomp false: wake p50 47–61 µs, park p50 60–81 µs).
  • Holding the cores out of deep idle (PM QoS 0) changed nothing on this host, unlike on the aarch64 reference host.
  • A cooperative park takes about as long as a forced one: the guest’s kick-to-doorbell path (interrupt, SCHED_FIFO park thread, doorbell exit) adds up to the same 60–80 µs (#74). Split up (2026-11-14, spec 09 §9): 4–32 µs from the kick to its injection, 16–64 µs in the guest to the doorbell, and 8–16 µs for KVM to handle the doorbell’s exit.

Unmodified guests: kicking the new owner’s CPU (measured, 2026-11-14)

#54. Setup: a bare-metal x86_64 host (AMD EPYC 9124, 16 cores with SMT, Ubuntu 7.0.0-42 kernel), pylond with scx_pylon on 3 managed CPUs and the default grace. Two 4-vCPU Ubuntu guests park inside KVM, without pv-pylon, and each spins on all 4 vCPUs, so every revocation is forced and parked vCPUs keep waking to share their VM’s CPUs. A script moves cores from one VM to the other every 50 ms by swapping their max_cores (1 and 3) over the control socket: about 590 handoffs per run. A host trace (signals, KVM exits, system calls, context switches on the managed CPUs) covered 20 s of each run.

Where the time went: most recipients (271 of 343 in the trace) weren’t on a CPU when pylond gave them a core: they were woken vCPUs waiting for their turn on a CPU their VM shares. A signal doesn’t queue a thread that is already runnable, and scx_pylon doesn’t watch the owner table, so nothing told the new owner’s CPU. When the donor parked and blocked, the recipient ran within 20 µs (p50); when the donor kept running (an interrupt woke it inside KVM at once), the recipient waited for a tick, 662 µs at the median. pylond now kicks the CPU after each assignment (pylon_kick_owner).

pylond’s histograms for the run: handoff 96 / 112 / 768 µs, wake 36 / 52 / 704 µs, park 52 / 60 / 60 µs.

  • Exit to the first handler: 5–8 µs; the 17 µs above was mostly the probes. With them, each step (get_signal, building the signal frame, the return to user space) took 1–4 µs.
  • A park’s extra handlers: pylond re-sends the kick 10, 20 and 40 µs after the first signal (REVOKE_RESIGNAL_US) while the donor hasn’t published PARKED. By then it has usually left KVM_RUN and is parking: 207 of 390 parks got two re-sends, 16–18 µs after the exit at the median, and each runs a handler. No single system call took over 4 µs at the median (KVM_GET_MSRS, KVM_GET_REGS, KVM_SET_MP_STATE, timer_settime).
  • A park’s tail: a donor that has published PARKED can be preempted by the new owner before its next KVM_RUN, and then waits about 1 ms. It is already parked, so the park latency doesn’t show it.
  • The wake and handoff tail: most signals that waited 0.2–3 ms for a CPU sent the vCPU to a CPU other than the one pylond gave it. scx_pylon kept a CPU’s woken turn after the CPU changed owner, so a sibling of the new owner, woken to share its VM’s old CPU, ran first and the new owner waited up to a tick. The new owner now takes the first turn (#104): wakes slower than 200 µs in the trace fell from 7–32 per run to 0–2.
  • The rest of pylond’s tail: with that fixed, pylond’s wake p99 stayed at 0.2–1.2 ms. pylond records a wake when the VMM publishes RUNNING, after the KVM_RUN exit, the wake eventfd read and KVM_SET_MP_STATE. Measured that way in the trace, the slow wakes match the histograms. The new owner left the guest 12–20 µs after the signal, and then a woken sibling of its VM, queued to share the CPU, preempted it at once and ran guest code for a whole tick, about 1 ms: the 100 µs share slice only ended at the tick. scx_pylon now lets a turn run 100 µs before a woken vCPU takes the CPU, and a timer ends each shared turn after 100 µs (#107). In two runs each against main, wakes over 0.5 ms in the trace went from 7–9 to 0, pylond’s wake p99 from 896–1,152 µs to 160 µs, its handoff p99 from 960–1,152 µs to 208 µs, and the median turn from 1,000 µs to 115 µs. The shared CPUs switch about 8 times as often (about 305,000 switches per 20 s against 37,000). Separately, the engine lost its CPU to a vCPU thread for 20 ms, 1–2 times per trace, which #105 fixes.

Pylon against upstream Cloud Hypervisor under overcommit (measured, 2026-11-15)

The suite in pylon/bench/overcommit/ (see its README.md). Two 4-vCPU guests run on three host CPUs, under three systems:

  • Pylon: pylond with scx_pylon manages the three CPUs.
  • Upstream: unmodified Cloud Hypervisor, both VMs pinned to the three CPUs and sharing them under the host’s scheduler.
  • Dedicated: unmodified Cloud Hypervisor, VM 1 pinned to one CPU and VM 2 to the other two. This is the split Pylon chose in every run below, held still.

Each guest runs a load for 150 s, measured from 40 s on. The loads are in workload.c: independent counting loops (the control), a spinlock, a spinning barrier, threads waking each other over pipes, and, next to a VM that wants every CPU, a ping-pong every millisecond.

What it shows:

  • Pylon wins where a guest’s threads spin while they wait for each other. At the barrier, both VMs do more rounds than under upstream, 3.3× in total, and twice what the dedicated split does. A VM’s extra vCPUs take 100 µs turns on its cores, where the host’s scheduler gives them a few milliseconds each, so a waiting round ends sooner.
  • Everywhere else, the same 100 µs turns cost 15–22% of the work. The dedicated split matches upstream, so the split isn’t the cost. With 1 ms turns (PYLON_SHARE_SLICE, an experimental build), Pylon comes within 3% of the dedicated split, and loses most of the barrier’s gain. The turn length trades one for the other.
  • Next to a busy VM, Pylon cuts the ping-pong’s p99 from about 4.7 ms to 0.23–0.33 ms. Pinning VM 1 to a CPU of its own gives about the same, 0.37 ms: the gain comes from VM 1 keeping a core. It kept it because it is at its min_cores and wakes every millisecond, so the busy VM got two CPUs and did 40% less than under upstream. Pylon would give the core back to an idle VM; this load doesn’t show that.
  • With equal weights, Pylon split the three cores 2 to 1 and kept that split for the whole run, so one VM did about half of what the other did. An urgent VM may take a core only while the other keeps its weighted share (spec 05 K7), which a 2 to 1 split never allows. The rotation build (#110) moves the core above an even split every 10 ms, which evens the VMs out, but their threads then used 3.05–3.33 CPUs. Each move is a forced preemption, and after a handoff without park scx_pylon let the donor run on any CPU for a 20 ms slice (#112 fixes that).
  • With both (7992b5ebd), the VMs’ threads use exactly the three CPUs, split 1.5 to 1.5 where both VMs want every core, and the work is back to the first Pylon column: the rotation’s gain in the rotation build came from the extra CPU time. In one spinlock run out of five, the rotation stopped at a 1 to 2 split after 20–30 s (#113). The ping-pong’s p99 was 315 µs.

Agentic inference and fine-tuning on GPUs (measured, 2026-11-15)

Where a VM’s time goes when it serves an AI agent, and when an agent VM and a fine-tuning VM share a host. This is a workload study, not a Pylon result: the VMs ran on Pylon’s VMM without --pylon, so the host’s scheduler placed their vCPUs. It shows what a Pylon policy would have to do for this workload.

Setup: a bare-metal x86_64 GPU host (2× AMD EPYC 7742, 8 NUMA nodes, Ubuntu 6.17 kernel, NVIDIA HGX A100 SXM4 40GB). Two VMs on Pylon’s VMM (built from main, 2026-11-15), each with one A100 passed through, 16 vCPUs and its memory on the GPUs’ NUMA node, pinned with taskset to host CPUs on that node. Guests: Ubuntu 24.04 (6.8 kernel), NVIDIA 580 open driver, vLLM 0.33.0.

  • Agent VM: vLLM serves Qwen2.5-7B-Instruct (prefix caching on, 32k context). 32 agent sessions each run tasks of 8 steps: an LLM call over the growing context (streamed, up to 256 tokens), then a real tool run on the CPU in the same VM. A user think time (5 s mean) separates tasks. Tool mixes, by weight:
    • light: read a file, rg, one pytest file, a small pandas job, one gcc -O0 compile of SQLite;
    • heavy: read a file 15, rg 20, the whole click test suite 30, a 4M-row pandas job 15, four gcc -O1 compiles of SQLite at once (as make -j4) 20.
  • Trainer VM: continuous LoRA fine-tuning (r 16, every linear layer) of Qwen2.5-1.5B-Instruct on Alpaca, bf16, batches of 4 × 2,048 tokens, with tokenizing, augmentation and packing in 6 DataLoader workers.

Each run measured 300 s after an 8-minute warm-up; the tool sequence is seeded, so every run replays the same mix. Guests sample /proc/stat, /proc/schedstat and the GPU each second; the host samples each VMM thread’s schedstat.

Where the time goes:

  • Light tools: the LLM call is 91% of a step, the GPU is always busy, and the VM uses 3.7 of its 16 CPUs. The GPU is the bottleneck.
  • Heavy tools: tools are 88% of a step (a build 62 s at the median, the test suite 36 s). The VM uses all 16 CPUs, about 59 threads wait for one on average, and the GPU idles a quarter of the time. CPUs are the bottleneck.
  • Throughput follows the CPUs: 63, 34 and 17 steps a minute on 16, 8 and 4. Each tool runs about as many times longer as the CPUs shrink.
  • The tools starve vLLM’s engine. On fewer CPUs its threads queue behind compilers and test runners: time to first token p99 rises from 0.65 to 2.66 s, and an LLM call takes 11.7 s instead of 4.3 s while the GPU is 22% busy.
  • Fine-tuning needs about one CPU. The trainer used 1.0–1.06 CPUs and kept its GPU 99% busy on 2, 4 or 16 CPUs, with no time waiting for data.
  • A static split wastes CPUs. Given 4 CPUs (R6) the trainer used one, and the agent did 7% less than when both VMs shared the 16 CPUs (R5), where it lost 2% against running alone (R2).
  • The VMM’s other threads (I/O, the device model) used no measurable CPU: the time is all in vCPUs.

What it means for Pylon: the cost here is how many cores each VM gets, and when, not how fast a core moves. Tools run for seconds to minutes; a 100 µs handoff doesn’t show. What would help is a policy that lends a VM’s idle cores (the trainer’s three in R6) to a VM whose threads queue, and keeps cores for an inference engine’s threads so that tools can’t starve it. Pylon can’t yet tell those threads apart inside a VM.

Limits of the data:

  • One run each. With heavy tools only 0–11 tasks finished in the window, so per-task times are rough; the per-step figures (87–1,311 steps a run) hold.
  • The tools ran in the agent’s VM. Production agents often run them in separate sandbox VMs, which is where moving cores between VMs would matter most; that layout wasn’t run.
  • LoRA fine-tuning only. Reinforcement learning runs rollouts and reward code on the CPU and would need far more.
  • Another VM ran on the host throughout (about 2 CPUs’ worth, not pinned to these CPUs).

Guest setup needed: with the A100s passed through, cuInit failed (CUDA_ERROR_NOT_INITIALIZED) until the guest set options nvidia_uvm uvm_disable_hmm=1; the image script does it. vLLM’s FlashInfer sampler compiles kernels with nvcc, which the guest lacks, so the agent runs with VLLM_USE_FLASHINFER_SAMPLER=0.

The harness is in pylon/bench/agentic-ai/; see Running the GPU workload study.

Running the GPU workload study

pylon/bench/agentic-ai/ holds the harness. It needs root, a host with two NVIDIA GPUs bound to vfio-pci, Cloud Hypervisor’s CLOUDHV.fd firmware, and about 250 GB of disk (the images are sparse; about 90 GB is written).

cd pylon/bench/agentic-ai
sudo ./mkimage.sh          # img/base.raw: Ubuntu 24.04, driver, vLLM, corpora
./mkmodels.sh              # img/models.raw: the two models and the dataset
cp img/base.raw img/agent.raw; cp img/base.raw img/trainer.raw
export FW=/path/to/CLOUDHV.fd NUMA=7 \
       AGENT_GPU=0000:87:00.0 TRAINER_GPU=0000:90:00.0
sudo -E WARM=600 ./scenario.sh smoke 112-127 112-127 smoke  # checks CUDA in both VMs
sudo -E FIRST=112 ./matrix.sh                                # R1–R7, about 2 hours
./analyze.py out R1-light-16c R2-heavy-16c                   # JSON summaries

Each VM boots, runs job/run.sh from its job disk, and powers off; results land in out/<run>/<vm>/. PARAMS overrides the job’s settings, for example PARAMS='{"agent":{"sessions":16}}' (the defaults are at the top of job/agent.py and job/train.py).
