Pylon

Enhancements

This page covers the planned changes to Pylon: first the work to make revocation cooperative, which is the most important, then smaller and later items. The authority is spec/06-guest-kick-path.md (a draft under review). Progress is tracked in spec/05-implementation-status.md as tracks 4 and 5.

Problems in the current revocation path

The handoff in Architecture expects the donor vCPU to be interrupted, finish any critical section, and park. Six problems prevent that today:

#ProblemEffect
P1The VMM creates per-vCPU kick eventfds and sends them to pylond, which writes them, but nothing turns them into a guest interrupt.The guest is never told about a revocation.
P2The park hook for HLT sits on VmExit::Reset. KVM handles HLT in the kernel, and also reports a guest triple fault as Reset.The hook never fires as intended, and a triple fault during a revocation is treated as a park instead of a reset.
P3The VMM parks on any exit to userspace while revoke_requested is set, without checking in_critical_section.A vCPU can be parked while it holds a guest lock.
P4pylon-guest-agent marks other vCPUs PARKED and clears their revoke_requested while they keep running.pylond hands the CPU over while the donor still runs, and the VMM never parks it.
P5When the deadline passes, pylond writes PARKED and clears revoke_requested for a vCPU that is still runnable.The donor never parks. It only moves elsewhere under the host scheduler.
P6state has three writers and no ownership rules.P4 and P5.

The design

Field ownership

Every field gets one writer (spec 06 §3), and PYLON_ABI_VERSION goes to 2 because the writer rules change, although the layout doesn’t:

FieldWriter
stateThe guest, only RUNNING → PARKING, for its own vCPU. The VMM, everything else. pylond never writes it.
revoke_requestedpylond sets it; the VMM clears it when it parks the vCPU.
forced_preempt_countMoves to the VMM, the only party that knows a forced park happened.
yield_count, last_yield_tscThe VMM.

Kick delivery: the pylon-kick PCI device

A small virtual PCI device, created with --pylon, with one MSI-X vector per vCPU (spec 06 §4.2). The guest driver allocates the vectors with managed affinity, so vector i interrupts vCPU i. The device installs the VMM’s kick eventfds, the ones pylond already has, as its MSI-X notifiers, so a write from pylond goes through the irqfd path and arrives as an interrupt. BAR0 exposes the magic, ABI version, vCPU count and the shared page’s address, plus a park doorbell; BAR1 holds the MSI-X table.

Implemented (S4) in vmm/src/pylon_kick.rs, as 1af4:10f0 (Q1). While the guest hasn’t enabled a vector, or has masked it, a kick waits in its eventfd and is delivered once the vector is enabled. A VM with --pylon now refuses to snapshot or migrate. Nothing in the guest uses the device yet: that is S5.

Alternatives the spec rejected: a raw vector chosen by the guest (Linux has no supported way for a module to own one), KVM_SIGNAL_MSI from pylond (it doesn’t hold the VM’s descriptor), ivshmem-doorbell (Cloud Hypervisor implements only ivshmem-plain), and a virtio device (too heavy for one doorbell and N interrupts).

Cooperative park: a doorbell, then a decision table

At a safe point, the guest writes state = PARKING and then any value to the PARK_DOORBELL register. That MMIO write exits to the VMM on the writing vCPU, so the vCPU runs no more guest code. The device’s handler does nothing (it must not block while holding the device’s lock). The existing post-exit hook decides (spec 06 §4.4):

staterevoke_requestedDeadlineAction
PARKINGanyanyCooperative park. A park without a revocation (an idle guest giving a core back) is allowed.
RUNNING1passedForced park; forced_preempt_count += 1.
RUNNING1not passedReturn: the guest hasn’t agreed and still has time.
RUNNING0—Return (the common case: one atomic load).

The VmExit::Reset hook is removed.

Forced park: a signal from pylond

Implemented (S2). When a deadline passes, pylond sends tgkill(vmm_pid, host_tid, kick_signal) (spec 06 §4.4–4.5). Cloud Hypervisor’s vCPU threads already ignore SIGRTMIN with a no-op handler, so KVM_RUN returns EINTR, the KVM backend reports VmExit::Ignore, and the post-exit hook force-parks. Details:

  • The VMM sends its own SIGRTMIN() as kick_signal when it registers, because the number depends on the libc. pylond accepts only a real-time signal, and doesn’t signal a VMM that sent none.
  • pylond learns the VMM’s PID from SO_PEERCRED and opens a pidfd for it. Before each signal it checks the process still exists, so a reused PID is never signalled.
  • The signal is resent every 10 µs, because one that arrives while the thread is outside KVM_RUN doesn’t stop the next guest entry.
  • pylond hands the CPU over only once the VMM has written PARKED. As a last resort it hands it over 50 µs after the deadline, counted separately as a handoff without park.
  • pylond no longer writes WAKING. It reserves a recipient through assigned_pcpu and reclaims a core only after the vCPU’s yield_count has moved (The arbitration engine).

The guest kernel module

pv-pylon (pylon/guest/linux/, spec 06 §4.6) binds to the device, maps the page, and allocates one MSI-X vector per vCPU.

  • Vectors. Vector i is pinned to CPU i whenever that CPU comes online. The kernel’s managed spreading isn’t used, because it doesn’t keep that order.
  • The kick. The kick handler wakes CPU i’s SCHED_FIFO park thread. A kick that lands on another CPU is forwarded to that thread, not dropped.
  • The park. The thread runs at a safe point. It sets the vCPU’s stranded_work_bitmap bit if other tasks are waiting, writes state = PARKING, then writes the doorbell. The vCPU stops at that write until pylond wakes it.
  • /dev/pylon. The module exposes the page there, and pylon-guest-agent maps it instead of /dev/mem. The agent has been telemetry-only since S3.

Still to do: keeping in_critical_section up to date, and making other vCPUs treat parked ones as preempted. Neither can be done from a module; both need guest kernel changes (spec 06 Q3).

S1–S4 have landed and S5 is built. With pv-pylon loaded, a revoked vCPU parks itself.

  • Stand-in pylond. All 800 test revocations parked cooperatively on Ubuntu 6.8 and 7.0 guests.
  • Not inside the grace period yet. Kick to PARKED takes about 20 µs, measured coarsely. That’s longer than the 8 µs grace, so under the real pylond many revocations still end in a forced park. S6 is about that latency.
  • The real-pylond run first hit a pylond bug with boot parks (spec 05 K7, now fixed). It now settles cores, and the guests then stall on a vCPU that stays parked (Q2).
  • S4 uses a provisional PCI ID (Q1).

Open questions

These are from spec 06 §10:

  • Q1. The PCI vendor and device ID for pylon-kick. For now it is 0x1AF4:0x10F0, from the range that QEMU’s PCI ID list leaves free for experiments. That range isn’t for shipped products, so a PCI-SIG vendor ID for CMKL is still to be requested, with a device ID under it before release.
  • Q2. Interrupts sent to a parked vCPU. A guest waiting for a TLB shootdown to finish spins until pylond wakes the target. Options: mark parked vCPUs preempted so the guest defers the flush, have the guest flag the target in stranded_work_bitmap, or have the VMM watch for pending interrupts on parked vCPUs. This also affects vCPUs parked at boot today.
  • Q3. The minimum guest kernel version, and where to hook in_critical_section.
  • Q4. Whether MSHV reports a signal-interrupted run the way KVM does.
  • Q5. How a VMM reconnects after pylond restarts.
  • Q6. Whether 50 µs is the right last-resort bound, or whether it should be per-VM policy.
